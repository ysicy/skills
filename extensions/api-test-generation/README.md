# api-test-generation — harness для генерации API-тестов

Harness (агентная обвязка) для GigaCode, который по **тест-кейсу** или **Swagger/OpenAPI-спецификации**
генерирует готовый API-автотест (pytest + Allure) и прогоняет его. Модель не пишет тест «одним
промптом»: оркестратор ведёт цепочку из 7 субагентов с разделёнными ролями
(анализ контура → требования → стратегия → генерация → ревью → исправление → валидация),
между ними стоят гейты (ревью, лимиты циклов, проверка соответствия кейсу), а детерминированные
шаги — разбор OpenAPI, хэш контура, дашборд — выполняют скрипты, а не модель. Цель — «дал ссылку на кейс → через ~10 минут готовый прогнанный тест».

Это README **для человека, который пользуется скиллом** (обычно QA-тестировщик). Внутренняя
документация пайплайна (для разработчиков скилла) живёт в `skills/api-test-generation/SKILL.md` и `skills/api-test-generation/references/common-principles.md`.

---

## Что умеет

- **Генерация по тест-кейсу Jira/Zephyr.** Достаточно ссылки вида
  `<JIRA_HOST>/secure/Tests.jspa#/testCase/<PROJECT_KEY>-TXXXX`.
- **Генерация по Swagger/OpenAPI.** По ссылке на `openapi.json`/`swagger` скилл парсит
  спецификацию, создаёт Pydantic-модели и генерирует тесты по ним.
- **Сборка тестового каркаса с нуля.** Если в проекте тестовой структуры нет — строится
  рабочая структура из шаблонов (`conftest.py`, HTTP-клиент, модели, конфиги, `pytest.ini`).
- **Работа с уже существующим контуром.** Если тесты уже есть — скилл дописывает новый тест
  в существующую структуру, **не трогая** написанное ранее.
- **Автономный прогон с самокоррекцией.** Тест генерируется, ревьюится, запускается.
  До 4 итераций исправления по замечаниям ревью и до 4 итераций по ошибкам запуска.
- **Итоговый отчёт.** По завершении выводится сводка прогона в `report.json`, краткий журнал
  (какие шаги прошли, длительность, вердикты по покрытию и качеству кода) и **накопительный
  дашборд** `test-report.html` по всем прогонам — «Сводка / Тесты / Замечания к кейсам / Расхождения
  стенда / Качество генерации / Хронология / Уроки». Собирает его скрипт `tools/report_tool`
  из `runs.jsonl`: токены на сборку не тратятся, цифры берутся из JUnit pytest.

## Что НЕ умеет (ограничения)

- Рассчитан на **Python-репозитории с pytest**. Другой язык/раннер — не поддерживается.
- Требует **доступ к стенду/окружению** для фактического прогона теста. Если стенд недоступен
  (нет доступа, токенов, сервис стабильно отвечает 4xx/5xx) — скилл **останавливается и
  запрашивает у вас недостающее**, а не «дожимает» наугад.
- Не заменяет ревью архитектуры тестов человеком: даёт автоматическое ревью и численный гейт
  качества, но финальное решение за вами.
- Генерация/публикация Allure-отчёта (HTML) **отключена** — Allure-атрибуты в коде остаются,
  но сам Allure-отчёт не публикуется. Результат — `report.json`, журнал в терминале и
  **сводный HTML-дэшборд с вкладками** (порождается самим пайплайном по эталону шаблона, не Allure).

## Что нужно от вас на входе

| Что | Когда | Пример |
|---|---|---|
| Ссылка на тест-кейс | Для генерации по кейсу | `<JIRA_HOST>/secure/Tests.jspa#/testCase/<PROJECT>-T1234` |
| Ссылка на Swagger/OpenAPI | Для генерации по спецификации | `https://…/openapi.json` |
| Доступ к стенду | Всегда (для прогона) | URL стенда, токены (`authToken`/`sessionToken` и т.п.), доступ по сети |

**Минимум — один из двух источников (кейс или Swagger) + доступ к стенду.** Всё остальное
скилл определяет сам.

В проекте должны быть Python и pytest, а также зависимости сгенерированного кода:
`pytest`, `requests`, `pydantic`, `allure-pytest`. Остальное — `<test_root>`, `base_url`,
схему авторизации, фикстуры и стиль — скилл берёт из вашего кода сам, вручную под него
ничего настраивать не нужно. Если тестового контура ещё нет, скилл соберёт каркас из шаблонов.

## Установка и настройка

Скилл ставится как GigaCode extension и в проект не копируется:

```bash
gigacode extensions install <путь-к-extension>
```

Подключение Jira MCP и разрешения агента в extension не входят — их задают в настройках
GigaCode пользователя или проекта. Пример настроек проекта (`.gigacode/settings.json`) — подставьте свои адреса и секреты:

```json
{
  "mcpServers": {
    "jira": {
      "type": "streamable-http",
      "httpUrl": "<JIRA_MCP_URL>",
      "headers": { "x-jira-token": "$secret:jira/x-jira-token" }
    }
  },
  "tools": { "approvalMode": "auto-edit" },
  "permissions": {
    "allow": [
      "Bash(python -m pytest *)",
      "Bash(python -m py_compile *)",
      "Bash(python \"<путь к skills/api-test-generation>/tools/hash_project.py\" *)",
      "Bash(python \"<путь к skills/api-test-generation>/tools/openapi_tool/main.py\" *)",
      "Bash(python \"<путь к skills/api-test-generation>/tools/report_tool/main.py\" *)",
      "Bash(git status *)",
      "Bash(git diff *)",
      "Agent(code-pattern-matcher)",
      "Agent(requirements-analyst)",
      "Agent(test-case-designer)",
      "Agent(test-generator)",
      "Agent(test-reviewer)",
      "Agent(test-fixer)",
      "Agent(test-validator)",
      "Skill(api-test-generation)",
      "mcp__jira__zephyr_get_test_case",
      "mcp__jira__zephyr_search_test_cases"
    ]
  }
}
```

- Скиллу нужно только **чтение** кейсов из Jira/Zephyr; инструменты записи в Jira разрешать не нужно.
- Правила для инструментов — с полным путём к конкретному скрипту и пробелом перед `*`: так разрешён только этот скрипт с аргументами, а не любой файл каталога.
- `approvalMode: "auto-edit"` автопринимает правки файлов агентами. Если в проекте требуется подтверждать каждую правку, уберите его: пайплайн продолжит работать, просто будет спрашивать.
- Общий `"Bash"` не добавляйте: он разрешает любую команду без подтверждения. Без правила на `python -m pytest` GigaCode будет спрашивать подтверждение на каждый прогон теста — это допустимо, просто менее автономно.
- Токены — только через `$secret:`, не открытым текстом.
- Добавьте `.gigacode/design/` в `.gitignore` проекта: там текст кейсов, ответы стенда и история прогонов. Если скилл собирает каркас с нуля, он делает это сам.

## Быстрый старт

В проекте с тестами запустите команду:

```
/api-test-generation <JIRA_HOST>/secure/Tests.jspa#/testCase/<PROJECT_KEY>-TXXXX
```

или

```
/api-test-generation https://…/openapi.json
```

Работает и обычная просьба в диалоге: «Сгенерируй автотест по кейсу …».

Пайплайн пройдёт 7 шагов автоматически, без вопросов между ними. Финальный автотест появится
в `<test_suites>/test_<feature>.py`, сводка прогона — в `report.json`.

## Когда вас спросят

Обращение к вам происходит **только в одном случае** — не хватает данных, которые скилл не
может получить сам:

- нет тела/параметров/URL запроса или текст тест-кейса неполный;
- нет доступа к стенду или сервис стабильно отвечает ошибками из-за данных (нужны валидные токены/ключи);
- требование неоднозначно и его нельзя вывести из кода/контура;
- исчерпаны лимиты самокоррекции (4 ревью-итерации / 4 попытки запуска) без результата.

В таких случаях скилл **останавливается** и просит только недостающее/решение, после чего
продолжает с того же места (не перезапуская всё заново).

## Как устроен результат прогона

В конце выводится краткий журнал-сводка, например:

```
## Прогон — <feature/эндпоинт>
| Шаг | Статус | Артефакт | Время | Попытки | Примечание |
|---|---|---|---|---|---|
| matcher | ✅/❌ | code-patterns.json | 0:12 | 1 | ... |
...
Гейт покрытия: <pass | questionable> — coverage_strategy=<N>
Гейт качества кода: <pass | questionable> — code_quality=<N>
Внешние блокеры: <blocked: да/нет — external_rate=<N>>
Итог: <тест прошёл / не прошёл — причина>
```

- **Гейт покрытия** — какая доля требований превратилась в тест-кейсы (считает дизайнер).
- **Гейт качества кода** — насколько честно код соответствует кейсу (ничего лишнего) и как
  «с наскока» сработал пайплайн.
- **Внешние блокеры** — какая доля сбоев вызвана стендом/данными, а не кодом.
- Вердикт `questionable` — мягкая пометка «код рабочий, но под вопросом»: смотрите код и
  сами решаете, править или допустить.

## Артефакты на диске (после прогона)

Всё находится в `.gigacode/design/` (актуальный срез последнего прогона):

| Файл | Содержимое |
|---|---|
| `code-patterns.json` | кэш структуры тестового контура |
| `requirements.json` | модель требований по кейсу |
| `test-cases.md` | спроектированные тест-кейсы/стратегия |
| `review-report.md` | отчёт ревьюера |
| `quality-gate.json` | метрики качества и вердикты гейтов |
| `report.json` | сводка прогона |
| `fix-history.md` | база опыта (не затирается между прогонами) |
| `runs.jsonl` | история прогонов, по строке на прогон (не затирается между прогонами) |
| `test-report.html` | накопительный дашборд по всем прогонам: тесты, замечания к кейсам, расхождения стенда, качество генерации; собирает `tools/report_tool` |

## Траблшутинг для пользователя

- **Стенд не отдаёт данные (4xx/5xx)** → проверьте доступы/токены; скилл запросит их и
  продолжит с того же шага. Это нормальная пауза, а не ошибка пайплайна.
- **Скилл просит уточнить данные кейса** → подскажите недостающее (тело, URL, параметры) —
  это ожидаемое поведение, он не «додумывает» за счёт точности проверок.
- **Тест упёрся в лимит итераций** → скилл остановится с отчётом о причинах; посмотрите на
  код/сводку и передайте решение (что исправить или одобрить).
- **Правки существующих тестов** → скилл **никогда не перетирает** уже написанные тесты:
  добавляет только новое. Если хотите переработать существующий тест — делайте это явно.
