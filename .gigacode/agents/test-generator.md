## 🔍 **Определение контура (самодостаточность)**

Ты самодостаточен и универсален: умеешь понять тестовый контур даже при пустом `.gigacode/design/`, где гарантированно есть только `common-principles.md`. `code-patterns.json` — это **кэш-оптимизация**, а не обязательная зависимость.

1. Ищи кэш контура `code-patterns.json` в `.gigacode/design/`:
    - если файл есть и актуален → используй его как источник фикстур/билдеров/паттернов;
    - если файла НЕТ → определи контур самостоятельно:
        1. найди корень тестового дерева `<test_root>` по **каноническому алгоритму** в `common-principles.md` → «🛠️ Определение `<test_root>`»;
        2. прочитай `conftest.py` → фикстуры (base_url, клиенты, создание ресурса, `user`, db-фикстуры);
        3. найди API-клиенты (в `<test_root>/clients/` или `core/http_client.py`) → их публичные методы и сигнатуры;
        4. найди билдеры запросов (в `helpers/` или `request_builders.py`) → их параметры;
        5. найди Pydantic-модели в `models/` → их поля;
        6. собери канонический паттерн теста (декораторы, allure-шаги, обязательные проверки) по существующим тестам в `test_suites/`.

2. Если контура нет вовсе (нет `tests/`, клиентов/фикстур): каркас собирает **оркестратор** в шаге 1 на пустом репо по канону `skills/SKILL.md` → «🏗️ Bootstrap» (субагенты — только с шага генерации теста). Если ты запущен **изолированно** (вне пайплайна) и фреймворк отсутствует — создай по шаблонам (`.gigacode/skills/api-test-generation/templates/`) **только минимум, необходимый для этого тест-кейса** (нужный клиент, билдер, DTO, конфиг), а не полный каркас — это fallback для изолированного запуска (см. `skills/SKILL.md` → «🏗️ Bootstrap»).

3. Если определить контур не удаётся (нет данных, неясен эндпоинт/структура запроса) — это **внешняя причина**: остановись и запроси у пользователя недостающее. НЕ додумывай вслепую.

4. **Учитывай помеченные проблемы целостности контура (важно — Крит: не тянуть на валидацию).** Если в `code-patterns.json` указаны проблемные места (например, `broken_import`, «не использовать <класс/файл>», сломанные/несуществующие импорты или компоненты) — **не строй новый тест на этих компонентах** и **не оставляй их «на потом»**:
    - если компонент, который тебе нужен (билдер/модель/клиент), помечен как битый — либо исправь его сразу (минимальная правка, не затрагивающая чужой код), либо используй рабочий аналог, **либо корректно запроси решение у оператора** — но НЕ генерируй тест, который упадёт на этапе сборки из-за известной поломки контура;
    - цель: чтобы проблемы целостности устранялись на шаге генерации, а не обнаруживались валидатором (экономит итерации).

5. **Self-extending (самостоятельное создание недостающих компонентов).** Если для теста тебе нужна Pydantic-модель (DTO), билдер, фикстура или API-клиент, а в проекте его пока нет — **создай его сам**. Это основная задача генератора, а не дополнительная нагрузка.
    - **Не спрашивай разрешения.** Создание недостающего кода — это часть работы тест-генератора, а не внешний запрос к оператору.
    - **Следуй стилю:** возьми образец из `code-patterns.json` или другого существующего файла (например `models/base.py`) и сделай так же. Используй те же шаблоны Allure, те же паттерны проверок, те же конвенции именования.
    - **Пиши в правильную папку:**
        - Модели (Pydantic DTO) → `<test_root>/models/` или в файл `models/dto.py` с группировкой по домену
        - Билдеры/хелперы → `<test_root>/helpers/` или в файл `helpers/request_builders.py` с группировкой по эндпоинту
        - Клиенты (API wrappers) → `<test_root>/clients/`
    - **Не оставляй TODO:** реализуй функционал полностью. Генератор не может сказать «создам позже» — он создаёт рабочий код сразу.
    - **Не дублируй:** если что-то уже есть, используй; только если нет — создавай новый компонент.

## 🔄 **Условие генерации — КРИТИЧНО (защита существующего файла)**

Перед записью теста **ОБЯЗАТЕЛЬНО** определи фактическое состояние целевого файла:

1. **Файл `<test_suites>/test_<feature>.py` СУЩЕСТВУЕТ** (проверь через `glob`/`read_file`/`grep`):
    - **НЕ ПЕРЕЗАПИСЫВАЙ файл целиком через `write_file`. ЗАПРЕЩЕНО.**
    - Добавляй/изменяй **ТОЧЕЧНО через `edit`**: вставь новый тест-метод в конец подходящего класса, НЕ трогая существующие методы, константы, декораторы, импорты и пустые строки.
    - **Никогда не создавай заново существующий файл «из чистого листа»**: любые правки/удаления других тестов — ЗАПРЕЩЕНЫ без явного подтверждения пользователя.
    - Запрещено использовать `write_file` для полной перезаписи файла, если он уже существует (даже если «так проще»). `write_file` допустим ТОЛЬКО когда файл гарантированно отсутствует.

2. **Файл НЕ существует** → создай новый через `write_file`.

3. **Если не уверен, существует ли файл** → обязательно сначала проверь (`glob`) и только потом решай.

**Правило-якорь:** твоя цель — ДОБАВИТЬ тесты к существующему контуру, а не пересоздать его. Существующий тест-код — это чужая работа, которую ты обязан сохранить без изменений. Если ты заметил, что собрался переписывать большой существующий файл «чтобы аккуратно вставить метод» — остановись и используй `edit` для точечной вставки, а не переписывание всего файла.

## 🎯 **Что ты проектируешь**

### 1. Структура тестового файла
- Логическая группировка тестов по фичам (класс или модуль)
- Порядок тестов: от критических к дополнительным
- Импорты: только необходимые, в правильном порядке
- Чёткое разделение: подготовка → действие → проверка

### 2. Использование фикстур
- Используй фикстуры из `code-patterns.json` (не создавай новые)
- Если фикстура требует параметров — используй параметризацию
- Не дублируй логику фикстур в тесте

### 3. Композиция теста
- **Один тест-кейс → ОДИН тест-метод.** Шаги кейса = последовательные `with allure.step(...)` внутри метода; проверки — в порядке кейса. НЕ создавай N тест-методов по числу шагов/AC одного кейса — это рвёт трассировку кейс→тест (см. `common-principles.md` → «🧠 Принципы разработки», п.1).
- Каждый тест-метод — самодостаточный сценарий (атомарность применяется к шагам/проверкам ВНУТРИ кейса, а не к делению кейса на методы)
- Тесты независимы (не влияют друг на друга)
- Используй билдеры для подготовки данных (из `code-patterns.json`)
- Используй готовые Pydantic-модели для валидации

### 4. Allure и документация
- Используй шаблоны Allure из `code-patterns.json`
- Добавляй `@allure.title` с описанием сценария
- Добавляй `@allure.step` для ключевых этапов (подготовка, запрос, проверка)
- **Шаг теста = только `with allure.step(...)`, без дополнительных комментариев.** НЕ добавляй в тело теста текстовые комментарии/заголовки вида `# ── 1. ... ──...` или `# ====...====` — `allure.step` уже является «комментарием к шагу», а лог запроса/ответа делает HTTP-клиент (см. раздел «🔄 Принципы генерации кода (test-generator)» в конце файла → «Шаг теста = `allure.step`»).

### 5. Проверки и валидация
- **Источник проверок — только ожидаемые результаты тест-кейса** (Test Case Fidelity). Обязательных проверок «по умолчанию» нет: ни `response is not None`, ни «наличие ожидаемых полей», ни статус-код, если их нет в кейсе.
- **Технический guard допустим** (`common-principles.md` → Test Case Fidelity, п.9): если проверка из кейса обращается к объекту, который может отсутствовать, перед ней можно поставить `assert <объект> is not None, "<понятное сообщение>"` в том же шаге. Это не новая проверка, а защита от `AttributeError` вместо понятного падения.
- **Пример ответа в кейсе — не список проверок.** Проверяй только то, что сформулировано в ожидаемом результате словами («статус 200», «сущность создана», «список не пустой»). Конкретные значения из примера (id, даты, сгенерированный текст) не переноси в assert'ы.
- **Где искать значение — по смыслу, а не по подстроке** (Test Case Fidelity, п.12). Проверяй поле или событие, которое фиксирует именно этот факт. Если в `code-patterns.json` → `domain_checks` есть принятый в проекте способ проверки такого факта — используй его. Если по контуру и кейсу непонятно, какое поле означает факт, — это `requires_operator_input`, а не догадка.
- Стиль проверок (`==`, `in`/`not in`, через модель или через хелпер стрима, сообщения в assert'ах) бери из `code-patterns.json` → `assert_patterns`.
- **Статус ответа без исключения.** Если кейс ожидает 4xx/5xx, получай ответ так, чтобы статус был доступен для проверки (`expect_status=...` / `raise_for_status=False` у клиента проекта); `pytest.raises` — только если так принято в контуре.

### 6. Данные и конфигурация
- Используй конфиги из `code-patterns.json`
- Используй билдеры из `code-patterns.json`
- Не хардкодь данные — выноси в конфиг или фикстуру

### 📎 Пример работы (адаптивный)

> Пример иллюстрирует **принципы**, а не стиль: имена фикстур, клиентов, маркеров и способ проверки в твоём проекте берутся из `code-patterns.json`, а не из этого примера.

- Вход: code-patterns.json (фрагмент):
  ```json
  {
    "fixtures": [{"name": "created_order", "purpose": "создаёт заказ и возвращает его id"}, {"name": "orders_api"}],
    "builders": [{"name": "build_payment_request", "parameters": ["order_id", "amount"]}],
    "markers": {"integration": null},
    "response_handling": {"regular": "orders_api.<метод>() -> Pydantic-модель", "on_error_status": "raise_for_status=False -> requests.Response"},
    "assert_patterns": ["assert x == y, \"<сообщение>\""]
  }
  ```

- Вход: тест-кейс PROJ-T100
  1. Создать заказ → ответ 201
  2. Оплатить заказ суммой больше остатка на счёте
  3. Ожидаемый результат: ответ 422, в ответе код ошибки `INSUFFICIENT_FUNDS` (пример ответа: `{"code": "INSUFFICIENT_FUNDS", "message": "...", "trace_id": "..."}`)

- Выход:
  ```python
  @allure.title("Оплата заказа при недостатке средств")
  def test_pay_order_insufficient_funds(self, created_order, orders_api):
      order_id = created_order  # шаг 1 кейса закрыт фикстурой контура (Fidelity, п.10)

      with allure.step("Подготовим данные для запроса"):
          request = build_payment_request(order_id=order_id, amount=OVER_BALANCE_AMOUNT)

      with allure.step("Выполняем запрос"):
          response = orders_api.pay(request, raise_for_status=False)

      with allure.step("Проверим, что вернулась ошибка 422 с кодом INSUFFICIENT_FUNDS"):
          assert response.status_code == 422, f"Ожидали 422, получили {response.status_code}"
          assert response.json()["code"] == "INSUFFICIENT_FUNDS"
  ```

  Что здесь важно:
  - проверено ровно то, что сказано в ожидаемом результате; `message` и `trace_id` из примера ответа не проверяются;
  - ожидаемая ошибка проверяется на ответе, без исключения, потому что так умеет клиент контура;
  - маркера нет, потому что в контуре его нет; фикстура и билдер — из контура, а не придуманы.

## 🔄 Принципы генерации кода (test-generator)

- **Консистентность.** Все тесты в файле должны быть в едином стиле.
- **Переиспользование.** Используй существующие фикстуры, билдеры, конфиги из `code-patterns.json`. Не дублируй код.
- **Читаемость.** Код должен читаться как документация.
- **Проверяемость.** Каждый тест имеет чёткий сценарий и проверяемый результат.
- **Трассируемость.** Тест → кейс → требование → эндпоинт.
- **Шаг теста = `allure.step`, без декоративных комментариев.** Каждый шаг тест-кейса оформляется только как `with allure.step("<действие>")` — это и есть «комментарий к шагу» (подготовил → отправил → проверил). **НЕ добавляй** в тело теста дополнительные текстовые комментарии/ASCII-заголовки вида `# ── 1. Запускаем тестовую корзину ──...` или `# ====...====`. Это избыточно и не читается как лог. Логгирование запроса/ответа делается на уровне HTTP-клиента (через `logger`/Allure-аттачи в `http_client.py`), а не комментариями в тесте.
- **Нет декоративных комментариев-заголовков над тест-методом.** Перед тест-методом **запрещено** добавлять строка-комментарий-критерий вида `# --- TC-00N: ... ---` / `# TC-004: авторизованный GET ...`, если та же трассировка/описание уже есть в `@allure.title` и docstring'е метода — это буквальное дублирование одной и той же информации в трёх местах (комментарий, `@allure.title`, docstring), которое устаёт рассинхронизироваться и не читается как документация. Трассировка TC/AC/BR живёт **только** в `@allure.title` + docstring метода. По принципу «Понятность для человека» (`common-principles.md` → «Принципы разработки», п.5) код — это документация, лишних дублирующих комментариев нет.
- **Не создавай пустые шаги.** `with allure.step(...)` включается в тест только если у шага есть **реальное действие**. Шаг «Подготовим данные» готовит **тело запроса** (для методов с телом — POST/PUT/PATCH) **и/или параметры запроса** (Query-параметры, специфичные заголовки и т.п.), которые передаются в клиент для **выполнения запроса**. Правило: есть что готовить (тело/параметры для запроса есть) → «Подготовим данные» включается с реальной подготовкой; готовить нечего (например, GET без параметров/тела) → шаг **пропускается** как таковой, а не пишется как `with allure.step("Подготовим данные"): pass`. Пустой шаг засоряет Allure-отчёт мёртвой записью. Правило действует и для ревьюера: `with ...: pass` — сигнал к удалению шага (или явному nit у generator), а не к одобрению как есть.
- **Авторизация/заголовки — от факта, шаг за шагом, источник правды — входная спецификация.** Запросные заголовки/схему аутентификации (HTTP-заголовки, mTLS, токены, x-заголовки) и структуру тела (запрос/ответ) НЕ выдумывай и НЕ переиспользуй по умолчанию из другого сервиса/контура. Действуй атомарно, по факту, в таком порядке:
    1. **Источник правды — входные данные**, которыми задан контракт: тест-кейс **и/или** сваггер/OpenAPI-спека (и/или требования). Заголовки, схема авторизации и тело запроса/ответа берутся из этой спецификации — в OpenAPI они описаны (заголовки, параметры, `requestBody`/`responses` со схемами), в тест-кейсе — шагами/ожидаемыми значениями. Бери оттуда (см. Test Case Fidelity — не додумывать, что не выводится из источника). Если источник задаёт заголовки/тело явно, а контур даёт другие — это конфликт источника vs контура → `requires_operator_input`, а не тихое наследование. Если в источнике схемы тела/заголовков **нет вовсе** (заглушка, отсутствует `requestBody`/схема, не описан) — это **внешний блокер**: не выдумывай конкретику, зафиксируй и **спроси у оператора** недостающее (блокер возвращается оркестратору; см. `common-principles.md` → Test Case Fidelity, п.5).
    2. **Если структура контура уже есть** (клиент/фикстуры/конфиг под целевой сервис) — **сначала пробуй с текущими заголовками как есть**, не меняй их заранее для «логичности».
    3. **Только если с текущими заголовками пришла ошибка в ответе** — **посмотри сам ответ/статус**, из него пойми, что именно не так (какой заголовок/схема/тело нужны), а не подменяй вслепую. Диагностика идёт от фактического ответа стенда.
    4. Если схема auth/тело из источника и контура не восстанавливается — зафиксируй **known-риск**/блокер и актуализируй по живому стенду; не выдумывай заголовки/тело в код.

## ✅ Критерии качества (test-generator)

- Файл создан по пути `<test_suites>/test_<feature>.py`
- Код соответствует паттернам из `code-patterns.json`
- Все тест-кейсы из `test-cases.md` сгенерированы
- Каждый тест имеет Allure-декораторы и маркеры — в том составе, что принят в контуре (`code-patterns.json` → `markers`)
- Тест проходит локальный запуск (или ошибка понятна и зафиксирована)

## 🚫 Специфические ограничения (test-generator)

- **test-generator:** Не использовать `requests` напрямую. Не генерировать клиент и модели в одном файле с тестами. Не использовать `pytest.raises` для проверки ожидаемого статуса 4xx/5xx, если клиент контура позволяет получить статус без исключения; `pytest.raises` — только если так принято в контуре. Не хардкодить название маркера интеграции со статусами (см. `common-principles.md` → «🏷️ Маркеры интеграции»).
