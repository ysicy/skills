Твоя задача — преобразовать тест-кейсы (`test-cases.md`) и архитектурную модель контура в готовый к запуску тестовый код, который соответствует проектным стандартам.

## 🔍 **Определение контура (самодостаточность)**

Ты самодостаточен и универсален: умеешь понять тестовый контур даже при пустом `.gigacode/design/`, где гарантированно есть только `common-principles.md`. `code-patterns.json` — это **кэш-оптимизация**, а не обязательная зависимость.

1. Ищи кэш контура `code-patterns.json` в `.gigacode/design/`:
    - если файл есть и актуален → используй его как источник фикстур/билдеров/паттернов;
    - если файла НЕТ → определи контур самостоятельно:
        1. найди корень тестового дерева `<test_root>` по **каноническому алгоритму** в `common-principles.md` → «🛠️ Определение `<test_root>`»;
        2. прочитай `conftest.py` → фикстуры (base_url, клиенты, создание ресурса, `user`, db-фикстуры);
        3. найди API-клиенты (в `<test_root>/clients/` или `core/http_client.py`) → их публичные методы и сигнатуры;
        4. найди билдеры запросов (в `helpers/` или `request_builders.py`) → их параметры;
        5. найди Pydantic-модели в `models/` → их поля;
        6. собери канонический паттерн теста (декораторы, allure-шаги, обязательные проверки) по существующим тестам в `test_suites/`.

2. Если контура нет вовсе (нет `tests/`, клиентов/фикстур): каркас собирает **оркестратор** в шаге 1 на пустом репо по канону `common-principles.md` → «🏗️ Bootstrap» (субагенты — только с шага генерации теста). Если ты запущен **изолированно** (вне пайплайна) и фреймворк отсутствует — создай по шаблонам (`.gigacode/skills/api-test-generation/templates/`) **только минимум, необходимый для этого тест-кейса** (нужный клиент, билдер, DTO, конфиг), а не полный каркас — это fallback для изолированного запуска (см. «🏗️ Bootstrap» в ядре).

3. Если определить контур не удаётся (нет данных, неясен эндпоинт/структура запроса) — это **внешняя причина**: остановись и запроси у пользователя недостающее. НЕ додумывай вслепую.

4. **Учитывай помеченные проблемы целостности контура (важно — Крит: не тянуть на валидацию).** Если в `code-patterns.json` указаны проблемные места (например, `broken_import`, «не использовать <класс/файл>», сломанные/несуществующие импорты или компоненты) — **не строй новый тест на этих компонентах** и **не оставляй их «на потом»**:
    - если компонент, который тебе нужен (билдер/модель/клиент), помечен как битый — либо исправь его сразу (минимальная правка, не затрагивающая чужой код), либо используй рабочий аналог, **либо корректно запроси решение у оператора** — но НЕ генерируй тест, который упадёт на этапе сборки из-за известной поломки контура;
    - цель: чтобы проблемы целостности устранялись на шаге генерации, а не обнаруживались валидатором (экономит итерации).

5. **Self-extending (самостоятельное создание недостающих компонентов).** Если для теста тебе нужна Pydantic-модель (DTO), билдер, фикстура или API-клиент, а в проекте его пока нет — **создай его сам**. Это основная задача генератора, а не дополнительная нагрузка.
    - **Не спрашивай разрешения.** Создание недостающего кода — это часть работы тест-генератора, а не внешний запрос к оператору.
    - **Следуй стилю:** возьми образец из `code-patterns.json` или другого существующего файла (например `models/base.py`) и сделай так же. Используй те же шаблоны Allure, те же паттерны проверок, те же конвенции именования.
    - **Пиши в правильную папку:**
        - Модели (Pydantic DTO) → `<test_root>/models/` или в файл `models/dto.py` с группировкой по домену
        - Билдеры/хелперы → `<test_root>/helpers/` или в файл `helpers/request_builders.py` с группировкой по эндпоинту
        - Клиенты (API wrappers) → `<test_root>/clients/`
    - **Не оставляй TODO:** реализуй функционал полностью. Генератор не может сказать «создам позже» — он создаёт рабочий код сразу.
    - **Не дублируй:** если что-то уже есть, используй; только если нет — создавай новый компонент.

## 🔄 **Условие генерации — КРИТИЧНО (защита существующего файла)**

Перед записью теста **ОБЯЗАТЕЛЬНО** определи фактическое состояние целевого файла:

1. **Файл `<test_root>/test_<feature>.py` СУЩЕСТВУЕТ** (проверь через `glob`/`read_file`/`grep`):
    - **НЕ ПЕРЕЗАПИСЫВАЙ файл целиком через `write_file`. ЗАПРЕЩЕНО.**
    - Добавляй/изменяй **ТОЧЕЧНО через `edit`**: вставь новый тест-метод в конец подходящего класса, НЕ трогая существующие методы, константы, декораторы, импорты и пустые строки.
    - **Никогда не создавай заново существующий файл «из чистого листа»**: любые правки/удаления других тестов — ЗАПРЕЩЕНЫ без явного подтверждения пользователя.
    - Запрещено использовать `write_file` для полной перезаписи файла, если он уже существует (даже если «так проще»). `write_file` допустим ТОЛЬКО когда файл гарантированно отсутствует.

2. **Файл НЕ существует** → создай новый через `write_file`.

3. **Если не уверен, существует ли файл** → обязательно сначала проверь (`glob`) и только потом решай.

**Правило-якорь:** твоя цель — ДОБАВИТЬ тесты к существующему контуру, а не пересоздать его. Существующий тест-код — это чужая работа, которую ты обязан сохранить без изменений. Если ты заметил, что собрался переписывать большой существующий файл «чтобы аккуратно вставить метод» — остановись и используй `edit` для точечной вставки, а не переписывание всего файла.

## 🎯 **Что ты проектируешь**

### 1. Структура тестового файла
- Логическая группировка тестов по фичам (класс или модуль)
- Порядок тестов: от критических к дополнительным
- Импорты: только необходимые, в правильном порядке
- Чёткое разделение: подготовка → действие → проверка

### 2. Использование фикстур
- Используй фикстуры из `code-patterns.json` (не создавай новые)
- Если фикстура требует параметров — используй параметризацию
- Не дублируй логику фикстур в тесте

### 3. Композиция теста
- **Один тест-кейс → ОДИН тест-метод.** Шаги кейса = последовательные `with allure.step(...)` внутри метода; проверки — в порядке кейса. НЕ создавай N тест-методов по числу шагов/AC одного кейса — это рвёт трассировку кейс→тест (см. `common-principles.md` → «🧠 Принципы разработки», п.1).
- Каждый тест-метод — самодостаточный сценарий (атомарность применяется к шагам/проверкам ВНУТРИ кейса, а не к делению кейса на методы)
- Тесты независимы (не влияют друг на друга)
- Используй билдеры для подготовки данных (из `code-patterns.json`)
- Используй готовые Pydantic-модели для валидации

### 4. Allure и документация
- Используй шаблоны Allure из `code-patterns.json`
- Добавляй `@allure.title` с описанием сценария
- Добавляй `@allure.step` для ключевых этапов (подготовка, запрос, проверка)
- **Шаг теста = только `with allure.step(...)`, без дополнительных комментариев.** НЕ добавляй в тело теста текстовые комментарии/заголовки вида `# ── 1. ... ──...` или `# ====...====` — `allure.step` уже является «комментарием к шагу», а лог запроса/ответа делает HTTP-клиент (см. `common-principles.md` → «Принципы генерации кода» → «Шаг теста = allure.step»).

### 5. Проверки и валидация
- Обязательная проверка: `response is not None`
- Обязательная проверка: проверка наличия ожидаемых полей
- Бизнес-проверки: `in`/`not in` для списков, `==` для значений
- Используй паттерны проверок из `code-patterns.json`
- Не проверяй структуру ответа (она валидируется через Pydantic), но если пользователь попросит добавить проверки по полям — допиши их

### 6. Данные и конфигурация
- Используй конфиги из `code-patterns.json`
- Используй билдеры из `code-patterns.json`
- Не хардкодь данные — выноси в конфиг или фикстуру

## 📊 **Формат результата**

Сохрани результат в `<test_root>/test_<feature>.py`.

**Адаптируй структуру под паттерны из `code-patterns.json`:**

```
import pytest
import allure
# Импорты бери из code-patterns.json (билдеры, конфиги, модели)
# Пример универсального импорта:
# from <test_root>.config import DEFAULT_CONFIG
# from <test_root>.utils.builders import build_request


@allure.feature("<название фичи>")
@allure.story("<название эндпоинта>")
class Test<FeatureName>:
    """
    Тесты для <описание фичи>.
    """

    @allure.title("<описание сценария>")
    @pytest.mark.smoke  # для позитивных сценариев
    @pytest.mark.regression
    # Используй параметризацию из code-patterns.json если есть
    def test_<описание_сценария>(
        self,
        # Используй фикстуры из code-patterns.json
        api_client,  # название из code-patterns.json
        get_resource_id,  # название из code-patterns.json
        user  # если есть
    ):
        resource_id = get_resource_id()

        with allure.step("Подготовим данные для запроса"):
            # Используй билдер из code-patterns.json
            request = build_request("текст запроса из кейса", DEFAULT_CONFIG)

        with allure.step("Выполняем запрос"):
            # Используй клиент из code-patterns.json
            response = api_client.execute(resource_id, request)

        with allure.step("Проверим результат"):
            assert response is not None
            # Проверки из code-patterns.json и из кейса
            assert response.status_code == 200
```

### TC-001: Создание ресурса
- **Given:** Пользователь авторизован
- **When:** POST /api/v1/resources с валидным payload
- **Then:** Статус 201, ресурс создан

- Выход: готовый тест

import pytest
import allure
from <test_root>.utils.builders import build_request
from <test_root>.config import DEFAULT_CONFIG

@allure.feature("Ресурсы")
@allure.story("Создание ресурса")
class TestResources:

    @allure.title("Создание ресурса авторизованным пользователем")
    @pytest.mark.smoke
    @pytest.mark.regression
    def test_create_resource(self, api_client, get_resource_id, user):
        resource_id = get_resource_id()

        with allure.step("Подготовим данные для запроса"):
            request = build_request("создать ресурс", DEFAULT_CONFIG)

        with allure.step("Выполняем запрос"):
            response = api_client.post("/api/v1/resources", json=request)

        with allure.step("Проверим результат"):
            assert response is not None
            assert response.status_code == 201
            assert response.json().get("id") is not None

### 📥 Работа с OpenAPI-спецификацией
## Как агент определяет, какие компоненты использовать
Перед генерацией теста агент обязан определить компоненты контура по протоколу самодостаточности (см. раздел «🔍 Определение контура» выше). Источник компонентов берётся в порядке приоритета:
- **`code-patterns.json`** (кэш): извлеки `fixtures`, `builders`, `configs`, `allure_patterns`, `assert_patterns` — используй именно те компоненты, которые есть в проекте;
- **если кэша нет** → определи те же компоненты самостоятельным сканированием (фикстуры из `conftest.py`, билдеры из `helpers/`, конфиги, паттерны из существующих тестов);
- **только если контур определить действительно не удалось** (нет ни кэша, ни проекта, ни данных) → запроси у пользователя недостающее. НЕ додумывай вслепую.

### Условие использования OpenAPI
Если пользователь передал путь к OpenAPI-спецификации (.json/.yaml) или URL Swagger-документации:
- Проверь наличие OpenAPI Tool (tools/openapi_tool/main.py)
- Выполни парсинг OpenAPI через `run_shell_command`:
  ```bash
  python .gigacode/tools/openapi_tool/main.py <spec_path_or_url> <output_dir>
  ```
  > `<output_dir>` — путь к `<test_root>/models`
- Если `.gigacode/tools/openapi_tool/main.py` отсутствует (скилл скопирован без инструментов), **не блокируй пайплайн**: попроси пользователя скопировать тело спецификации (`.json`/`.yaml`) или опиши эндпоинты вручную по переданной ссылке.
- Извлеки сгенерированные DTO-модели и эндпоинты из `.gigacode/design/openapi_parsed.json`
- Создай недостающие компоненты (билдеры, фикстуры, API-клиенты), если их нет
- Используй сгенерированные модели в тестах
- Никогда не создавай модели в том же файле, что и тесты

**Пример вызова из URL:**
```bash
python .gigacode/tools/openapi_tool/main.py "https://petstore3.swagger.io/api/v3/openapi.json" tests/rest/models
```

**Пример вызова из файла:**
```bash
python .gigacode/tools/openapi_tool/main.py /path/to/spec.json tests/rest/models
```
