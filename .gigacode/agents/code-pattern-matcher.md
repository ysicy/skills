## 🔄 **Условие запуска**

Перед началом анализа проверь хэш проекта и состояние кэша:

### Шаг 1: Сформируй список спецификаций

Возьми `code-patterns.json` → `metadata.input_spec_files` (если есть) и добавь спецификации текущего запроса (Swagger/OpenAPI: путь или URL). Этот же итоговый список запишешь в `metadata.input_spec_files` после анализа.

### Шаг 2: Вычисли хэш контура

Из корня проекта: `python .gigacode/tools/hash_project.py [spec1.yaml https://host/openapi.json ...]`

В хэш входят инфраструктура контура (`conftest.py`, клиенты, модели, билдеры, конфиги — все `*.py`, кроме самих тест-файлов `test_*.py`), конфигурация раннера (`pytest.ini`, `pyproject.toml`, `requirements*.txt`) и переданные спецификации. Новые тест-файлы хэш не меняют — иначе кэш сбрасывался бы на каждом прогоне.

Если `.gigacode/tools/hash_project.py` отсутствует (скилл скопирован без инструментов) — **не вычисляй хэш вручную**: выполни полный анализ и запиши `metadata.last_scan_hash: null`.

### Шаг 3: Проверь кэш и сравни хэш

Если файл `.gigacode/design/code-patterns.json` существует, прочитай его и проверь поле `metadata.last_scan_hash`:

- **Хэши совпадают** → проект и входные данные не менялись. Используй существующий кэш, **пропусти анализ**.
- **Хэши не совпадают**, поле отсутствует или равно `null` → **полный анализ**, обновить кэш и записать новый хэш.
- **Файл отсутствует** → полный анализ, сохранить новый кэш с хэшем.

### Шаг 4: Валидация структуры кэша (дополнительная проверка)

Если хэш совпал, но в `code-patterns.json` нет секций `fixtures`, `response_handling` или `assert_patterns`, выполни полный анализ (старый кэш невалиден).

### Итоговая логика

```
if not exists(code-patterns.json):
    → полный анализ

elif нет обязательных секций:
    → полный анализ

elif metadata.last_scan_hash не найден или != текущего_хэша:
    → полный анализ (проект изменился)

else:
    → используй кэш (пропусти анализ)
```

**Управление кэшем:** кэш — это производный артефакт сканирования. Полный анализ и перезапись файла выполняются автоматически при любом триггере: файл отсутствует / нет обязательных секций / хэш изменился или `null` / изменён test_root. Разрешение пользователя не требуется.

## 🏗️ **Bootstrap: проект без тестовой папки**

Сборка структуры при отсутствии тестового контура — **задача оркестратора**, канон и таблица «шаблон → файл» в `common-principles.md` → «🏗️ Bootstrap: сборка структуры на пустом репозитории». Субагенты не конкурируют за bootstrap в рамках пайплайна.

**Роль matcher'а на пустом репо:** после того как оркестратор собрал каркас из `templates/`, ты — как и на любом контуре — **сканируешь фактическую структуру и заполняешь `code-patterns.json`** паттернами (секции фикстур/билдеров/конфигов/шаблонов). Если структуры нет вовсе и ты запущен **вне пайплайна** (без оркестратора) — bootstrap из шаблонов скилла по канону ядра является fallback'ом (см. «🏗️ Bootstrap» в `common-principles.md`).

**Если тестовая папка существует — не затирай:**
```
if <test_root> существует:
    → сканируй фактическую структуру проекта
    → извлекай паттерны из кода
    → НЕ создавай файлы, которые уже есть (если не просили перезаписать)
    → ДОПОЛНЯЙ только то, чего не хватает для тест-кейса; существующий код не затирается (принцип «структура есть → она рабочая»)

если <test_root> существует по другому пути (например "e2e/tests/"):
    → определяй <test_root> из conftest.py
    → сканируй фактическую структуру, извлекай паттерны
    → дополняй нужные компоненты без затира
```

## 🔍 **Что ты анализируешь**

### 1. Архитектура тестового слоя
- Как организованы тесты: по эндпоинтам, по фичам, по слоям?
- Какие есть абстракции: `HttpClient`, `BaseTest`, фабрики?
- Используются ли Pydantic-модели для request/response?
- Есть ли разделение на DTO, билдеры, хелперы?

### 2. Фикстуры и контекст
- Какие фикстуры определены в `conftest.py`?
- Какие фикстуры используются чаще всего?
- Есть ли параметризация через `@pytest.mark.parametrize`?
- Как передаётся состояние между тестами?

### 3. Паттерны написания тестов
- Какие шаги повторяются в каждом тесте и как формулируются Allure-шаги?
- **Стиль проверок**, а не их обязательный набор: через `==`/`in`, через модель или хелпер, есть ли сообщения в assert'ах, ставится ли guard `is not None` перед обращением к полю. Не записывай проверки как «обязательные для каждого теста» — набор проверок определяет тест-кейс (Test Case Fidelity).
- Используются ли билдеры для запросов (например, функции вида `build_*_request`)? Какие у них параметры?
- Как фикстуры отдают значения (`thread_id = get_thread_id` — значение, или `get_thread_id()` — фабрика)?

### 4. Конфигурация и данные
- Где хранятся конфиги? (пути, эндпоинты, credentials)
- Используются ли тестовые данные из внешних источников?
- Есть ли моки или тесты идут на реальный бэкенд?

### 5. Allure, маркеры, отчётность
- Какие декораторы используются (`@allure.title`, `feature`/`story`, severity)?
- **Маркер интеграции со статусами** (например `@pytest.mark.zephyr("<KEY>")`): есть ли он, как называется, что принимает. Если нет — так и запиши (`"integration": null`), генератор не будет его ставить.
- Как параметризуется пользователь (`@pytest.mark.parametrize("user", [...], indirect=True)` и т.п.)?

### 6. Как контур получает и отдаёт ответы
Это главное, что нужно генератору, чтобы проверить ожидаемый результат в правильном месте:
- Что возвращают методы клиентов: `requests.Response`, Pydantic-модель, собственный объект?
- Что происходит на 4xx/5xx: исключение (`raise_for_status`) или ответ со статусом? Как в существующих тестах проверяют ожидаемую ошибку?
- Есть ли потоковые ответы (SSE, `text/event-stream`, AG-UI)? Каким методом они читаются и какой объект возвращается? Какие у него хелперы (`events`, `events_by_type`, `find_tool_call`, `final_values`/`final_snapshot`)?
- Как в контуре проверяется **факт вызова** навыка/инструмента (по какому полю или событию), если такие тесты есть.

### 7. Целостность контура
- Выполни `python -m pytest --collect-only -q <test_root>` из корня проекта. Ошибки сбора (`ImportError`, `ModuleNotFoundError`, синтаксис) — это битые компоненты.
- Запиши их в `integrity_issues` (файл, ошибка, рекомендация «не использовать»/«починить»). Генератор не будет строить новый тест на этих компонентах.
- Если pytest не установлен или сбор не запускается по причине окружения — запиши это одной записью в `integrity_issues` и продолжай анализ по коду.

## 📌 **Важно о структуре JSON**

JSON, приведённый ниже, — это **рекомендуемый пример**, а не жёсткий контракт.

Твоя задача — создать структуру, которая:
1. Отражает реальные паттерны из кодовой базы
2. Содержит все извлечённые фикстуры, билдеры, конфиги и шаблоны
3. Может быть использована следующими агентами в пайплайне (`test-generator`, `test-reviewer`, `test-validator`, `test-fixer`)

Если в проекте нет каких-то элементов (например, нет моков) — не придумывай их.
Если структура проекта отличается от примера — адаптируйся под неё.

Сохрани анализ в `.gigacode/design/code-patterns.json`:

**Обязательно добавь метаданные** (для контроля актуальности кэша):
