# 🔥 🚨 **КРИТИЧЕСКОЕ ПРАВИЛО: ОБЯЗАТЕЛЬНАЯ ЦЕПОЧКА АГЕНТОВ**

**Когда пользователь просит сгенерировать автотест — ты ОБЯЗАН пройти полный пайплайн через всех 7 агентов в строгом порядке.**

**🚦 ПЕРВЫЙ ШАГ-ГЕЙТ (при любом входном тест-кейсе/ссылке/эндпоинте):**
1. Твоё **первое и единственное** действие после получения входных данных — вызвать `code-pattern-matcher` через `Agent tool` (Step 1). Ничего не анализируй, не парь входные данные, не строй ментальную модель сам — СРАЗУ запускай агента.
2. До тех пор, пока цепочка из 7 агентов не завершена **полностью**, ты не имеешь права:
    - самостоятельно разбирать/писать тестовый код,
    - проектировать тест-кейсы, моделировать требования, подбирать фикстуры/билдеры "в уме",
    - перескакивать к генерации, минуя шаги matcher→analyst→designer→generator.
3. Каждый шаг — **отдельный вызов `Agent tool`**. Не выполняй работу под-агента сам и не поручай нескольким агентам выполнять работу одного шага.

**Тебе КАТЕГОРИЧЕСКИ запрещено:**
- ❌ Генерировать тестовый код самостоятельно, минуя агентов
- ❌ Писать тест "в один проход" без анализа, проектирования, ревью и валидации
- ❌ Пропускать любой шаг пайплайна, даже если тест кажется "простым"
- ❌ Делегировать часть шагов и выполнять другие самостоятельно
- ❌ Сначала читать структуру проекта/тест-кейс "для понимания" и писать код вместо запуска Step 1 — входной тест-кейс обрабатывает исключительно пайплайн

**Пайплайн — это НЕ опция, НЕ рекомендация. Это обязательный протокол.**

## 🔗 Полная цепочка (строгий порядок)

```
Входные данные (тест-кейс / шаги / эндпоинт)
        │
        ▼
  Step 1: code-pattern-matcher    → .gigacode/design/code-patterns.json
        │ (code-patterns.json готов)
        ▼
  Step 2: requirements-analyst    → .gigacode/design/requirements.json
        │ (requirements.json готов)
        ▼
  Step 3: test-case-designer      → .gigacode/design/test-cases.md
        │ (test-cases.md готов)
        ▼
  Step 4: test-generator          → <test_suites>/test_<feature>.py
        │ (тест-файл создан)
        ▼
  Step 5: test-reviewer           → отчёт с замечаниями
        │ (есть замечания)
        ▼
  Step 6: test-fixer              → исправленный тест
  [цикл ← reviewer, макс 4 раза]
        │ (ревью пройдено)
        ▼
  Step 7: test-validator          → отчёт валидации
        │ (тест зелёный)
        ▼
  Step 8: report (оркестратор)    → сводка прогона (report.json)
        │
        ▼
  Готовый тест + сводка прогона
```

**Финальный шаг `report` (выполняет оркестратор после зелёного прогона):**

1. Собирает **машиночитаемый отчёт прогона** по протоколу раздела «📇 Машиночитаемый отчёт прогона» (в конце этого файла):
    - перезаписывает актуальным срезом `.gigacode/design/report.json` (единый файл, без накопления истории). История — в git и `fix-history.md`;
    - источник секций: журнал прогона + `.gigacode/design/quality-gate.json` + результат валидации.

2. Генерирует **человекочитаемый HTML-отчёт с вкладками** (`.gigacode/design/test-report-<scope>.html`) — замена Allure для оператора. Шаблон доступен в `.gigacode/skills/api-test-generation/templates/report_template.html`.
    - Публикует через `artifact` для интерактивного просмотра; заголовок `Отчёт по сваггеру <scope>`.
    - Вкладки: Сводка, Тесты, Карта TC→AC, Эндпоинты, Метрики, Блокеры, Уроки.
    - **НАКОПЛЕНИЕ:** это **один общий дашборд на scope**, а не отчёт по каждому кейсу. При каждом прогоне агент читает ВСЕ имеющиеся артефакты (`test-cases.md`, `fix-history.md`, `quality-gate.json`, `openapi-<scope>.yaml`) и пересобирает файл заново — новые тесты/TC/AC автоматически попадают в сводку. Не перезаписывает из чистой головы (это невозможно — данные в проекте); всегда регенерирует по полным данным из `.gigacode/design/`.
    - Все цифры заполняются из артефактов проекта (не хардкодятся, не берутся из других проектов).
    - Если шаблон не найден или генерация не удалась — операция НЕ блокирует пайплайн, оператор видит предупреждение.

## 📊 Журнал прогона (сводка для оператора)

Оркестратор ведёт **краткий сводный журнал** каждого прогона для наблюдаемости оператора (без дампа сырых логов агентов). Формат выводится после каждого шага и в конце цикла:

```text
## Прогон — <feature/эндпоинт>
| Шаг | Статус | Артефакт | Время | Попытки | Примечание |
|---|---|---|---|---|---|
| matcher | ✅/❌ | code-patterns.json | 0:12 | 1 | ... |
| analyst | ✅/❌ | requirements.json | 0:15 | 1 | ... |
| designer | ✅/❌ | test-cases.md | 0:10 | 1 | ... |
| generator | ✅/❌ | test_<feature>.py | 0:20 | 1 | ... |
| reviewer | ✅/❌ | отчёт | 0:14 | 1 | ... |
| fixer | ✅/❌ | — | 0:00 | 0 | ... |
| validator | ✅/❌ | pytest результат | 1:12 | 1 | ... |
| report | ✅/❌ | report.json + HTML-отчёт | 0:15 | 1 | ... |
Блокер: нет | <внешний: причина> |
Гейт покрытия: <pass | questionable> — coverage_strategy=<N>, порог=<0.7> |
Гейт качества кода: <pass | questionable> — code_quality=<N>, порог=<0.7> |
Внешние блокеры: <blocked: да/нет — external_rate=<N>> |
Итог: <тест прошёл / не прошёл — причина>
Всего: <суммарное время>
```

**Гейты качества** — строки в конце журнала: покрытие стратегии (`coverage_strategy`) считает designer на шаге проектирования; качество кода (`code_quality`) и сигнал внешних блокеров (`blocked`) считает validator по протоколу `agents/test-validator.md` → «📊 Метрики качества и пороговый гейт». Вердикт `questionable` = мягкая пометка «под вопросом» (не жёсткий блок): код рабочий, но оператор сам решает — править или допустить. Подробности — в той же секции.

Правила:
- **Статус** — ✅ прошел / ❌ заблокирован / ⏳ ожидает.
- **Артефакт** — что создано/изменено на шаге.
- **Время** — длительность шага (мин:сек). Оркестратор фиксирует в момент завершения шага.
- **Попытки** — число запусков/итераций субагента на шаге (для ревью-цикла и валидатора с лимитом 4).
- **Примечание** — 1 короткая строка (важность для оператора: внешний блокер, 4 итерации, замечание).
- **Блокер** — если агент вернул внешний блокер, указать его кратко (для оператора сразу видно, где вмешаться).
- **Всего** — суммарное время пайплайна (в конце прогона).
- Журнал — это **оркестраторская сводка**, а не замена артефактов (requirements/test-cases/fix-history остаются на диске).

## 📋 Как вызывать агентов

**Каждый шаг — отдельный вызов через Agent tool. Не выполняй шаги самостоятельно.**

> **Запуск субагентов ТОЛЬКО в фоне.** Каждый вызов шага обязан передавать
> `run_in_background: true` (или не передавать вовсе, т.к. фон — поведение по умолчанию
> для top-level субагентов). **Никогда** не используй `run_in_background: false` для шагов
> пайплайна, которые выполняют команды (`run_shell_command`): синхронный запуск переводит
> их в интерактивный режим и `ask`-запрос остановит прогон в ожидании оператора. Фоновый
> запуск применяет `permissions.allow` без интерактивного ожидания — это обеспечивает
> автономию у вас и у всех, кто скопирует скилл, независимо от их `settings.json`. Ожидание
> завершения — строго по `task-notification`, продолжение — по фактическим артефактам
> (см. также п.2a и п.6 в «🚀 АВТОНОМНОСТЬ ОРКЕСТРАТОРА»).

> **Обязанность запуска:** вызов субагентов — инициатива оркестратора, а НЕ по указанию
> оператора. Не жди «запусти субагентов» — запускай сам при генерации теста и при
> любых правках тест-кода (писать/править тест самому — запрещено, это делают
> `test-generator`/`test-fixer`). Скелет инфраструктуры контура на пустом репо собирает
> оркестратор из `templates/`, субагенты подключаются с шага генерации теста.
> Полное правило — в разделе «🤖 Оркестратор и субагенты: обязанность запуска» (в конце этого файла).

> **🚀 АВТОНОМНОСТЬ ОРКЕСТРАТОРА (без запросов на подтверждение команд):**
> Пайплайн работает полностью автономно («кинул кейс → через 10 минут готово»). Оператор
> НЕ должен подтверждать/разрешать отдельные команды внутри пайплайна. Правила:
> 1. **Командные шаги выполняют субагенты, а не оркестратор.** Запуск pytest выполняет
     >    `test-validator` (у него есть `run_shell_command`); правки кода — `test-fixer`/`test-generator`;
     >    применение артефактов — соответствующие агенты. Оркестратор НЕ запускает тесты и НЕ
     >    правит код сам (иначе возникает лишний запрос на команду). Если валидатор по
     >    техническим причинам не смог запустить (нет shell) — он возвращает команду в отчёте,
     >    а оркестратор выполняет её БЕЗ запроса подтверждения у оператора.
> 2. **Внутри пайплайна подтверждение у оператора НЕ запрашивается** ни на запуск pytest,
     >    ни на правки файлов, ни на чтение/перезапись артефактов `.gigacode/design/`, ни на
     >    обновление `fix-history.md`/`quality-gate.json`/`report.json`. Это внутренние шаги скилла.
     > 2a. **Субагенты шагов пайплайна запускай ТОЛЬКО в фоне (`run_in_background: true`).**
     >    Синхронный запуск (`run_in_background: false`) переводит субагентов в интерактивный
     >    режим: их `run_shell_command` начинает ждать подтверждение оператора и останавливает
     >    прогон на каждом `ask`. Фоновый запуск (по умолчанию для top-level субагентов) применяет
     >    `permissions.allow` и не ждёт интерактивного подтверждения — это и есть гарантия
     >    автономии во всех сессиях и у всех, кто скопирует скилл, независимо от их `settings.json`.
     >    Ожидание завершения фонового шага — строго по `task-notification` (см. п.6), продолжение
     >    по фактическому состоянию артефактов, без таймеров/будильников.
> 3. **Единственное допустимое обращение к оператору** — нехватка входных данных, которые
     >    невозможно вывести из кейса/проекта (внешний блокер: стенд 403 с просьбой валидного
     >    `authToken`/`sessionToken`/токена, отсутствие данных, выбор из неоднозначности, решение
     >    оператора). Это НЕ «разрешение на команду», а запрос недостающих данных — он остаётся
     >    обязательным и не отменяется автономностью (см. «⏸️ Персистентность внешнего блокера»).
> 4. Если оператор всё же вручную вмешался в середине (прервал, задал вопрос) — продолжить
     >    с того же места, не перезапуская цепочку, и не «повторять запрос на команду».
> 5. **Системный отказ/отклонение `run_shell_command` ≠ подтверждение и ≠ блокер.** Откат
     >    одной формы команды на уровне рантайма — не «разрешение не выполнять» и не повод
     >    останавливаться/спрашивать. Действуй автономно: в пределах итерации пробуй эквивалентную
     >    форму команды (убрать/сменить флаг, обёртку, цепочку) до получения результата. Если
     >    несколько эквивалентных форм явно запрещены именно по этой операции — тогда это внешний/
     >    инфраструктурный блокер: зафиксируй в `fix-history.md` и запроси оператора. Правило про
     >    необход прямого запрета через суррогатную команду сохраняется (см. `agents/test-validator.md`).
> 6. **Ожидание фоновых агентов — ТОЛЬКО по `task-notification`, никаких будильников.**
     >    НЕ используй `loop_wakeup`/таймеры, чтобы «будить себя» и проверять, завершился ли
     >    фоновый субагент: фоновый агент сам присылает уведомление о завершении, и это
     >    единственный сигнал для продолжения. Если нужно подтвердить готовность артефакта —
     >    читай файл напрямую (`read_file`), а не планируй проверку на таймер. Продолжение
     >    пайплайна — по фактическому состоянию артефактов, без планирования будущих запусков
     >    и без запросов к оператору внутри прогона.
     > **Итог:** пайплайн самодостаточен для команд; операция подтверждается только когда реально
     > не хватает данных. Оркестратор обязан различать «запрос на выполнение команды» (никогда) и
     > «запрос недостающих входных данных» (обязательно при внешнем блокере).

```

agent(description: "Анализ паттернов проекта", prompt: "...", subagent_type: "code-pattern-matcher")
```

## 🗂️ **Управление `code-patterns.json`**

**Принцип самодостаточности:** этот файл — **кэш-оптимизация, а НЕ обязательная зависимость.** Пайплайн обязан отработать по любому тест-кейсу даже при пустом `.gigacode/design/`, где гарантированно есть только `common-principles.md`. Каждый агент умеет самостоятельно определить контур (найти `<test_root>`, `conftest.py`, фикстуры, клиенты, билдеры, паттерны) по протоколу «🔍 Определение контура» в своём промпте. `common-principles.md` всегда доставляется агентам как единственный источник правил.

Файл `.gigacode/design/code-patterns.json` — это **кэш** результатов сканирования тестового контура (создаёт и обновляет `code-pattern-matcher` на шаге 1). Он не хранится вручную и всегда должен соответствовать текущей структуре проекта.

**Когда удалить/пересканировать `code-patterns.json`:**
- **Пользователь удалил или переименовал файлы** тестового контура (модули, сьюты, клиенты, модели) → удали `code-patterns.json`, чтобы `code-pattern-matcher` выполнил полный анализ заново.
- **Проект изменился значительно** (новая структура, добавлены/убран крупные компоненты, изменён `test_root`) → перезапусти `code-pattern-matcher` (шаг 1) для получения актуальных паттернов.
- **Не используй старый `code-patterns.json`, если структура проекта изменилась** — устаревший кэш даст неверные фикстуры/билдеры/паттерны для генератора.

**Что НЕ делать:**
- Не правишь содержимое `code-patterns.json` вручную (правки вручную расходятся со сканированием) — при изменениях проекта полагайся на пересканирование через `code-pattern-matcher`.
- Не жди «неявной» инвалидации: если ты заметил рассинхрон кэша и фактического контура — явно удали файл или запусти матчер.

> Это правило дополняет логику `code-pattern-matcher` (файл отсутствует / нет обязательных секций / хэш контура изменился → полный анализ). Здесь заданы явные триггеры, когда пересканирование необходимо инициировать сразу, не дожидаясь, пока матчер сам заметит рассинхрон.
>
> **Согласовано с правилом матчера:** перезапись `code-patterns.json` выполняется автоматически при любом триггере (файл отсутствует / нет обязательных секций / хэш контура изменился / удалены-переименованы файлы контура / изменён `test_root`), разрешение пользователя не требуется. Правило «не править кэш вручную» остаётся в силе. Если контур не менялся — кэш не трогаем.


## 🔁 Модульность пайплайна (`continue_from`)

Пайплайн умеет стартовать не с шага 1, а с **первого недостающего/упавшего шага**, переиспользуя уже готовые валидные артефакты. Это экономит ресурсы (особенно в проектах, где один контур обслуживает много тест-кейсов) и повышает надёжность при повторных/смежных прогонах.

**Логика при приёме тест-кейса:**
1. Определи `<test_root>` и проверь наличие/валидность артефактов по порядку:
    - `code-patterns.json` — шаг matcher **не пропускается**: он запускается всегда и сам решает по хэшу контура, переиспользовать кэш (`cache_hit`, быстро) или пересканировать (`full_scan`).
    - `requirements.json` — валиден, если `_meta.case_key == <текущий кейс>` → шаг analyst можно пропустить. Иначе артефакт не совпадает → шаг analyst выполняется заново.
    - `test-cases.md` — валиден, если `_meta.case_key == <текущий кейс>` → шаг designer можно пропустить. Иначе артефакт не совпадает → шаг designer выполняется заново.
2. Стартуй с первого недостающего шага; шаги **generator → reviewer → fixer → validator выполняются всегда** (код в любом случае должен быть проверен и валидирован).
3. **Продолжение после сбоя/блокера.** Если прогон прервался на шаге N по внешней причине (стенд, данные, блокер), а артефакты шагов 1..N-1 уже валидны — при повторном запуске начни с шага N, не перегоняя готовые. Не перезапускай весь пайплайн с нуля из-за сбоя на позднем шаге.
4. **Принудительный полный прогон** — явный запрос оператора «перезапусти всё» / флаг `full`: игнорируй артефакты и пройди все 7 шагов с шага 1 (нужно, когда структура/требования изменились и кэш устарел).

**Важно:** переиспользование артефактов — это экономия, а не обход шагов качества. Generator/reviewer/validator не пропускаются никогда. `Test Case Fidelity` и правила `common-principles.md` действуют всегда.

### Параллельная генерация набора кейсов

Если вход — **набор из нескольких тест-кейсов/сценариев**, генерацию допускается распараллелить. Параллелизм применяется **только после** того, как `matcher → analyst → designer` уже отработали и дали полный контекст (контур + модель требований + стратегия).

1. Оркестратор запускает несколько `test-generator` параллельно — по одному кейсу (или малой группе) на субагента.
2. **Каждый параллельный генератор получает готовые артефакты** (`code-patterns.json`, `requirements.json`, `test-cases.md` своего кейса) и **не сканирует репозиторий заново** — он генерирует по готовой модели, а не исследует контур.
3. Каждый параллельный генератор пишет свой изолированный результат (отдельный файл/метод) — конфликты записи исключаются разграничением.
4. Число параллельных субагентов ограничено (по умолчанию ≤ 4), чтобы не деградировать по качеству и не упереться в лимиты.
5. После генерации — **единый общий проход** `test-reviewer` → (при необходимости `test-fixer`) → `test-validator` по всему набору тестовых сценариев. Качество и валидация всегда последовательны и общие.
6. Для **одного** тест-кейса/сценария — поведение как в базовом пайплайне (без распараллеливания).
7. **Синхронизация с continue_from:** если генерация распараллелена, каждый агент пишет результаты в свои изолированные файлы/методы без конфликтов. При повторном прогоне (continue_from) оркестратор проверяет **все case_keys** в `_meta` и определяет, какие кейсы уже обработаны, а какие нужно перегенерировать.

### 🔗 Взаимодействие с механизмом черновиков

Для шагов, которые могут писать в общие артефакты одновременно (`requirements-analyst`, `test-case-designer`), применяется протокол из раздела «🗂️ Версионирование артефактов пайплайна» (в конце этого файла):
- Каждый агент пишет во **временный изолированный файл-черновик** `requirements-<case>.tmp.json` / `test-cases-<case>.tmp.md`.
- **Оркестратор на завершении шага сводит все черновики в единый постоянный файл** (`requirements.json` / `test-cases.md`) и **удаляет черновики**.
- Постоянное хранилище всегда — единый файл с актуальным срезом.

Это гарантирует, что parallel generate → review → fix → validator работает как единый конвейер без конфликтов записи.

## 🔄 **Процесс генерации (профессиональный пайплайн)**

### Инициализация структуры проекта

Канон `test_root` — в `common-principles.md`, bootstrap — в разделе «🏗️ Bootstrap» в конце этого файла. **Владелец bootstrap — оркестратор**; субагенты подключаются к уже готовой структуре с шага генерации теста.

Перед вызовом `requirements-analyst` оркестратор:
1. Определи `<test_root>` — корень тестового дерева (см. секцию ниже).
2. Проверь наличие структуры проекта.
3. Если структуры нет — собери её по шаблонам скилла (`templates/`) по канону раздела «🏗️ Bootstrap» (в конце этого файла).
4. После создания каждого Python-файла проверь его через `python -m py_compile <путь>` (из корня проекта). Если есть синтаксическая ошибка — исправь через `edit` или удали и пересоздай через `write_file` с правильной версией шаблона. Не запускай агентов на сломанном проекте.
5. Если структура есть — используй как есть (не затирай, дополняй только недостающее для кейса).

### Определение `<test_root>`

Перед началом работы агент **обязан** определить корень тестового дерева (`<test_root>`) — путь, который используется всеми агентами вместо хардкода. Определение — по **каноническому алгоритму** в `common-principles.md` → «🛠️ Определение `<test_root>`».

- Скилл универсален: корень выводится из **фактической структуры проекта**, своя схема папок не навязывается (структура есть → она рабочая).
- Если структуры нет — bootstrap из шаблонов скилла (`templates/`).

**Примеры** (иллюстрация, полный алгоритм — в ядре):
- `conftest.py` найден в `./tests/` → `<test_root> = "tests"`
- `conftest.py` найден в `./e2e/tests/` → `<test_root> = "e2e/tests"`
- `pytest.ini` найден в `./` → `<test_root> = "tests"` (если рядом есть папка `tests/`)
- Ничего не найдено → `<test_root> = "tests"` (дефолт)

**Важно:** `<test_root>` определяется один раз в начале пайплайна и передаётся всем агентам. Все пути в агентах — относительные от `<test_root>`.

### Сбор и анализ требований (`requirements-analyst`)
- Определи бизнес-контекст: зачем нужен эндпоинт, какие сценарии покрывает
- Выдели сущности, поля, бизнес-правила и ограничения
- Построй ментальную модель данных
- Зафиксируй acceptance criteria из требований (даже если не явные)

### Проектирование тестовой стратегии (`test-case-designer`)

Режим зависит от источника:
- **Вход — тест-кейс (Jira/Zephyr или текст шагов).** Один кейс → один сценарий. Designer ничего не добавляет, а делает кейс однозначным для генератора: для каждого ожидаемого результата фиксирует, **где** он проверяется (поле/событие ответа) и **как** (равенство, наличие, непустота), отмечает шаги, закрытые фикстурами, и шаги вне API (Test Case Fidelity, п.10–14). Приоритеты P0–P3 не применяются.
- **Вход — OpenAPI/требования.** Сценарии строятся по спецификации и упорядочиваются по приоритетам P0–P3 за один проход, без остановок для подтверждения. Интерактивный по-батчевый режим — только по явной просьбе оператора («генерируй по приоритетам», «покажи P0»).

В обоих режимах — только то, что выводится из источника: негативные, пограничные и нефункциональные сценарии (таймауты, ретраи, конкурентность) не добавляются, если их нет во входных данных.

### Генерация кода (`test-generator`)
- Используй существующие Pydantic-модели (не генерируй новые, если есть готовые)
- Проектируй читаемый, поддерживаемый код с учётом SOLID-принципов
- Добавь Allure-декораторы (`@allure.title`, `@allure.feature`, `@allure.story`, `@allure.step`)
- Продумай уровни логирования и отладочной информации для CI/CD
- Исключи хардкод: вынеси данные в конфиги или фикстуры

### Код-ревью (`test-reviewer`)
- Проверь сгенерированный тест по чеклисту качества
- Если тест проходит все пункты → переходи к валидации
- Если есть замечания → отправь на доработку `test-fixer`

Полный чеклист ревью — в `agents/test-reviewer.md`; критерии качества ревью — там же, раздел «✅ Критерии качества (test-reviewer)».

### Исправление замечаний (`test-fixer`)
- Получи отчёт от `test-reviewer`
- Исправь код теста строго по замечаниям из отчёта
- Не трогай то, что не указано в отчёте
- После исправления → верни код на повторное ревью (`test-reviewer`)
- Цикл `reviewer → fixer → reviewer` повторяй до 4 раз
- Если после 4 циклов замечания остались — передай управление пользователю

### Валидация и самокоррекция (`test-validator`)
- Запусти сгенерированный тест локально (или в CI-подобном окружении)
- Проанализируй ошибки: что упало, почему, как это исправить
- Выполни не более 4 итераций самокоррекции:
    - после каждой ошибки — диагностируй и исправляй
    - если после 4 итераций тест не прошёл — сдайся и запроси помощь пользователя (с детальным отчётом)
- **По завершении** посчитай гейт качества кода и сигнал внешних блокеров по протоколу `agents/test-validator.md` → «📊 Метрики качества и пороговый гейт» (`code_quality = fidelity*0.6 + cost*0.4`, `blocked` при `external_rate >= 0.5`), включи в итоговый `.gigacode/design/quality-gate.json` секцию `coverage_strategy` (посчитана designer'ом) и запиши туда результат. Вердикты (`pass` / `questionable`) и `blocked` оркестратор вносит в журнал прогона (строки «Гейт покрытия» / «Гейт качества кода» / «Внешние блокеры»).

### 🔁 Маршрутизация при неудачном запуске

Если сгенерированный тест **не собрался или упал при выполнении** — не переигрывай пайплайн с нуля. Пройденные стадии (matcher/analyst/designer/generator) уже дали артефакты. Активируй только хвост цепочки в строгом порядке:

1. `test-reviewer` — определить *почему* код мог не работать (по желанию, если включён режим полного прохода).
2. `test-fixer` — разобрать ошибку и исправить код точечно.
3. `test-validator` — перезапустить и итерировать.

**Запрещено:**
- ❌ Перегенерировать требования/кейсы/код заново из-за одной ошибки выполнения.
- ❌ Останавливаться после «тест написан, но упал» без запуска хвоста цепочки.

### 🚦 Классификация причины сбоя

Классификация ошибок («кодовая» — чини через `test-fixer`→`test-validator`; «внешняя» — СТОП и запрос к пользователю, не чинить вслепую) — в `agents/test-validator.md` и `agents/test-fixer.md`. Полные списки причин и формат отчёта об итоге сбоя (включая запись в `.gigacode/design/fix-history.md`) — там же.

### 🔗 Передача контекста между агентами

Контекст между агентами передаётся двумя способами: через **файлы-артефакты** и через **промпты** вызова агента. Соблюдай следующие правила:

**Через файлы (обязательно):** каждый агент пишет свой артефакт на диск, следующий читает его оттуда. Не переноси содержимое артефактов «в чат» — они должны жить в файлах:
- matcher → `code-patterns.json`
- analyst → `requirements.json`
- designer → `test-cases.md`
- reviewer → `.gigacode/design/review-report.md`
- generator → `<test_suites>/test_<feature>.py`
- validator → `fix-history.md`

> **📌 ПЕРЕДАЧА КОНТЕКСТА — ТОЛЬКО ЧЕРЕЗ ФАЙЛЫ НА ДИСКЕ. `send_message` для субагентов пайплайна НЕ используется.**
> Субагенты пайплайна работают последовательно, по одному на шаг, и обмениваются данными исключительно через файлы-артефакты и промпты вызова. `send_message` (возобновление завершённого/работающего агента по `task_id`) **не является** механизмом передачи контекста следующему агенту и **не входит** в протокол. Правила:
> 1. **Не используй `send_message` между шагами.** Контекст следующему субагенту доставляется артефактом на диске и/или текстом промпта при новом вызове `Agent`. Не зови агента обратно через `send_message`, чтобы «передать контекст» или «дожать» работу.
> 2. **Проверяй запись артефакта ПОСЛЕ каждого шага.** По завершении шага оркестратор ОБЯЗАН проверить через `read_file`/`glob`, что артефакт фактически создан (например, тест-файл генератора, `code-patterns.json` матчера и т.д.), прежде чем запускать следующий шаг.
> 3. **Если субагент завершился, не записав артефакт** (сказал «напишу», но файла нет) — **не пиши код/артефакт сам** и **не перезапускай весь пайплайн**. Перезапусти **этого же субагента новым вызовом `Agent`** с той же инструкцией (с указанием, что файл не создан), и повторяй, пока артефакт не появится.
> 4. Это не отключает подтверждение оператора в рантайме: если сам рантайм запрашивает подтверждение на какой-то инструмент — оно всё равно учитывается; правило лишь убирает `send_message` из протокола пайплайна как ненужный шаг.

**Отчёт ревьюера — через файл, а не промпт:** `test-reviewer` сохраняет отчёт в `.gigacode/design/review-report.md` (у него есть `write_file`, актуальный срез). При вызове `test-fixer` передай ему ссылку на этот файл — он прочитает отчёт **с диска**. Это персистентно и переживает `continue_from`/блокеры, в отличие от передачи «через промпт». Держать `review-report.md` в актуальном состоянии — обязанность ревьюера.

**Доставка опыта (база `fix-history.md`):** формат и правила записи — в `agents/test-validator.md` → «💾 Опыт накопления (`fix-history.md`)», обязанность оркестратора — в разделе «💾 Сохранность опыта» (в конце этого файла). При запуске агентов передавай в их промпт инструкцию прочитать `.gigacode/design/fix-history.md` (если существует), чтобы учесть прошлые сбои по этой фиче:
- `test-validator` и `test-fixer` — учитывают историю при диагностике/исправлении.
- `test-generator` / `test-case-designer` — история это **контекст-предупреждение**, НЕ источник шагов: не выдумывать проверки/сценарии из истории (источник — тест-кейс, см. Test Case Fidelity).
- Дисклеймер оркестратора: история доставляется как **контекст**, но не как правка `common-principles.md`; источник правил не изменяется автоматически.

### ⏸️ Персистентность внешнего блокера

Если какой-либо агент вернул **внешний блокер** (стенд недоступен, 4xx/5xx из-за данных, не хватает входных):
1. **Останови пайплайн** — не запускай следующих агентов.
2. **Сохрани статус блокера** в `.gigacode/design/fix-history.md` (агент, причина, запрошенные данные) — оркестратор обязан пережить паузу и не «забыть» причину между перезапусками.
   > Не теряй запись: если агент не сохранил её сам (нет write/shell) — он передаёт готовый текст дословно, а оркестратор обязан обеспечить запись в `fix-history.md`. Ответственность и механика — в разделе «💾 Сохранность опыта» (в конце этого файла). Это часть самообучения скилла.
3. **Запроси у пользователя** недостающие данные.
4. После получения ответа **продолжи с того же агента**, который выдал блокер — НЕ с начала цепочки.

## 📂 Статус файлов в `.gigacode/design/`: постоянные vs нагенерированные

Файлы в `.gigacode/design/` делятся на **две категории** по происхождению и жизненному циклу. Это деление — основа для понимания «что гарантированно есть», самодостаточности агентов и fallback-поведения.

| Категория | Файл | Происхождение | Поведение |
|---|---|---|---|
| **Постоянный** | `common-principles.md` | Ядро правил, входит в состав скилла/команды | **Не генерируется пайплайном и не удаляется.** Доставляется агенту как единственный источник правил. В норме всегда присутствует |
| **Нагенерированные** | `code-patterns.json`, `requirements.json`, `test-cases.md`, `review-report.md`, `quality-gate.json`, `report.json`, `fix-history.md` | Продукты шагов пайплайна | **Создаются и перезаписываются** на каждом прогоне (актуальный срез). При **первом** прогоне (или после очистки `design/`) могут **отсутствовать** |

**Правила:**
1. **`common-principles.md` — постоянный вход, не артефакт.** Оркестратор обязан доставлять его каждому агенту перед работой; агенты при самодостаточности всегда опираются на него (см. раздел «🧠 Принципы разработки» выше — где какие правила). Он не «нагенерированный файл» и не подлежит перезаписи шагами пайплайна.
2. **Всё остальное в `design/` — производное.** Наличие любого нагенерированного файла — это оптимизация (кэш/актуальный срез прошлого прогона), а **не** обязательное предусловие.
3. **Самодостаточность относительно статусов.** Каждый агент обязан работать корректно **при отсутствии любых нагенерированных файлов**, полагаясь только на постоянный `common-principles.md` и фактическую структуру проекта. Фразы «при пустом `.gigacode/design/` гарантированно есть только `common-principles.md`» в промптах означают именно это: все нагенерированные файлы могут отсутствовать.
4. **`fix-history.md` — особый нагенерированный:** в отличие от остальных (актуальный срез с перезаписью) он **накапливается** и является базой опыта (см. «💾 Опыт накопления»). Он не «гарантированно есть» при первом прогоне, но после первого сбоя/прогона создаётся и пополняется.

**Следствие для fallback:** если на первом прогоне нет `code-patterns.json` / `requirements.json` / `test-cases.md` — это штатно (нет кэша/артефакта), агент определяет контур или генерирует заново. Отсутствие же `common-principles.md` — **аномалия** (повреждение контура скилла): агент работает по критичным правилам, зашитым в промпт (Test Case Fidelity, классификация причин, границы ролей), а оркестратор извещает оператора о необходимости восстановить ядро.

## 🎯 Целевой контур скилла (Python / pytest / Allure / Jira-Zephyr)

Скилл `api-test-generation` профильный для **Python-репозиториев**. Он генерирует API-тесты через
пайплайн 7 субагентов из тест-кейсов/требований. Ниже — чёткая рамка: что универсально (адаптируется
под любой Python-репозиторий), а что является требованием/ожиданием к контуру.

**Что универсально внутри Python-экосистемы (адаптируется автоматически):**
- Структура тестового дерева — `<test_root>` определяется динамически (`conftest.py`, `pytest.ini`,
  `pyproject.toml`, `tests/`), контур сканируется, а не хардкодится.
- Интеграция со статусами / маркеры — берётся из фактической структуры проекта, не выдумывается
  (см. «🏷️ Маркеры интеграции»). Если в проекте механизма нет — тест без маркера.
- Ключ Jira-проекта — плейсхолдер `<PROJECT_KEY>` подставляется из ссылки на кейс, не зашит.
- **Пустой репозиторий без API-тестов** — оркестратор собирает полную рабочую структуру **из шаблонов** (`templates/`): `conftest.py`, `rest/core/http_client.py`, `models/`, `config/`, `helpers/`, `test_suites/` (см. «🏗️ Bootstrap»). Это bootstrap-сценарий: шаблоны дают стартовый каркас, чтобы автотест запустился даже на голом Python-репо. На непустом контуре шаблоны **не применяются** к существующему коду — контур сканируется как факт и «дополняется, а не затирается».
- Повторное использование на новом репозитории — через кэш `code-patterns.json` и модульность пайплайна (`continue_from`)
    + модульность `continue_from` (не перегоняются валидные артефакты).

**Ожидания к контуру (ядро компетенции скилла):**
- **pytest** — раннер тестов; валидатор запускает `python -m pytest ...`, шаблоны и критерии построены на pytest.
- **Allure** — структура тестов (декораторы `@allure.*`, шаги — часть кода и `code-patterns.json`). Генерация/публикация Allure-отчёта отключена (шаг report их не запускает — см. «📇 Машиночитаемый отчёт прогона»). Если в проекте Allure нет — скилл не «ломается»,
  но Allure-атрибуты опускаются (берём из `code-patterns.json`).
- **Jira-Zephyr** (или копирование шагов кейса) — источник тест-кейсов.

**Что это значит на практике:**
- Скилл рассчитан на **Python-репозитории с pytest**; это профильная специализация, а не ограничение.
- Перенос на другой Python-проект: структура/маркеры/ключ проекта подстроятся автоматически;
  наличие pytest — необходимое условие запуска.
- Стек (pytest/Allure/Jira) — **документируемое ожидание**, а не скрытый недостаток: оно заявляется
  в описании скилла и понятно при ревью/публикации.

## 🛡️ Права агентов и автономность

**Факт набора инструментов каждого агента = строго тому, что указано в `frontmatter tools:` его файла (`.gigacode/agents/<agent>.md`).**

Профиль инструментов (единый источник правды, соответствует текущему frontmatter):

| Агент | Инструменты (frontmatter tools:) |
|---|---|
| `code-pattern-matcher` | `read_file`, `glob`, `grep_search`, `list_directory`, `write_file`, `edit`, `run_shell_command` |
| `requirements-analyst` | `read_file`, `glob`, `write_file`, `edit`, `grep_search`, `run_shell_command` |
| `test-case-designer` | `read_file`, `write_file`, `edit`, `glob`, `grep_search`, `run_shell_command` |
| `test-generator` | `read_file`, `write_file`, `edit`, `glob`, `grep_search`, `run_shell_command` |
| `test-reviewer` | `read_file`, `grep_search`, `glob`, `write_file`, `run_shell_command` |
| `test-fixer` | `read_file`, `write_file`, `edit`, `grep_search`, `run_shell_command` |
| `test-validator` | `read_file`, `write_file`, `edit`, `grep_search`, `run_shell_command`, `glob` |

Правила:
1. **Реальный набор инструментов суб-агента == frontmatter `tools:`** этого агента. Это единственный источник правды для оркестратора при планировании шага.
2. **Проверка на рассинхрон.** Перед запуском суб-агента оркестратор сверяет заявленный `tools:` (frontmatter) с фактическим набором инструментов суб-агента. При расхождении — фиксирует в журнал прогона и **не полагается на текст** как на гарантию.
3. **Автономия суб-агентов.** Все суб-агенты имеют `run_shell_command` и `edit` и выполняют свою работу **самостоятельно**, без запроса подтверждения у оператора на отдельные команды/правки. Роль агента определяет, **что** он делает на своём шаге, а не ограничивает доступ к инструментам.
4. **Роли сохраняются (распределение шагов).** Даже при общей автономии сохраняется разграничение *кто что выполняет на своём шаге пайплайна*: pytest и запуск тестов — `test-validator` (при необходимости `test-generator`); правки уже сгенерированного кода — `test-fixer`/`test-generator`; артефакты пишет продуцирующий агент. Это предотвращает хаос конкурентных запусков, но **не** является ограничением доступа к инструментам.
5. **Глобальные настройки допустимы, если не ломают роли.** Широкие права в `permissions.allow` (например `Bash`, `Edit`, `Read`, `approvalMode: auto-edit`) **допустимы** и обеспечивают автономность; фактический доступ субагента определяется его ролью и границами шага, а не глобальным флагом как «разрешением команды». Глобальный флаг не отменяет распределения ролей по шагам.

   **Механизм автономного shell.** Авто-апрув shell-команд у субагента обеспечивается **только** правилами `permissions.allow` (например `"Bash"` или узкие `"Bash(python -m pytest *)"`). `approvalMode: auto-edit` **не** даёт авто-апрува shell: он автопро-пускает только edit-инструменты (`edit`/`write_file`/`notebook_edit`), а `run_shell_command` уходит в обычную ветку подтверждения (`ask`). В неинтерактивной/фоновой среде субагента `ask`-запрос не имеет UI и **отклоняется процесс-локальной политикой** с `default permission = deny`, даже если `"Bash"` есть в `permissions.allow`. Приоритет правил: `deny` > `ask` > `allow`. Поэтому:
    - если для конкретной команды нужен гарантированный авто-апрув — добавь явное узкое правило в `permissions.allow` (`.`gigacode/settings.json`);
    - если субагент видит `default permission = deny` на shell несмотря на `"Bash"` в project-level `allow` — проверь user/system-level `settings.json` (их `ask`/`deny` перекрывают project-level `allow` по приоритету);
6. **Внешний блокер не перекрывается автономией.** Автономия команд не означает «дожимать вслепую» при внешнем блокере (нет данных, стенд 4xx/5xx, неясное требование) — в этом случае агент останавливается и запрашивает недостающие входные данные у оператора (см. «⏸️ Персистентность внешнего блокера»). «Запрос недостающих данных» — единственное допустимое обращение к оператору и не является «запросом разрешения на команду».
7. **Публикуемая версия скилла** может поставлять права в широком (автономном) виде при сохранении распределения ролей по шагам. Верификация инструментов по frontmatter (правило 1-2) остаётся источником правды при планировании шага.

## 🗂️ Версионирование артефактов пайплайна

Каждый артефакт-продукт (`requirements.json`, `test-cases.md`, `quality-gate.json`, `report.json`) несёт служебные метаданные `_meta`/`metadata`:
- **`schema_version`** — версия структуры (сейчас `2.0`).
- **`generated_by` / `generated_at`** — кто и когда создал.
- **`case_key`/`case_keys`** — ключ входного тест-кейса (или список для набора).
- **`mode`** — `single`/`batch` (для наборного прогона).

**Единая схема хранения — «актуальный срез перезаписью».** Каждая сущность — **ровно один файл** с фиксированным именем (`.gigacode/design/requirements.json`, `test-cases.md`, `review-report.md`, `quality-gate.json`, `report.json`). Внутри хранится **только актуальный срез** — документ перезаписывается **целиком** на каждый новый прогон:

- **Без истории внутри файлов.** Прошлые прогоны в артефактах **не накапливаем** (`runs[]`/`history_limit` отсутствуют). История прогонов ведётся **вне файлов**: через `git` и через постоянную базу опыта `.gigacode/design/fix-history.md`. Артефакт всегда показывает текущее состояние.
- **Почему:** требования/стратегии/гейты/отчёты читаются агентами на каждом шаге; накопление истории раздувало бы файл и тянуло лишние токены при чтении. Актуальный срез — максимум читаемости и эффективности.
- **Набор:** для `single` тело — один кейс; для `batch` — в одном актуальном документе группируются все кейсы набора (массив `requirements[]`, секции `test-cases.md`, `case_keys` в `_meta`, `results_per_case` в отчёте).
- Запрещено плодить постоянные файлы вида `*-<case>`, `*-<batch>`, `*-<batch>-<timestamp>` рядом с базовым — существует только фиксированное имя файла.
- **Временные черновики параллельной генерации (исключение из запрета).** При параллельной работе нескольких агентов в один файл (например, несколько `requirements-analyst`/`test-case-designer` по кейсам набора) каждый агент может писать во **временный изолированный файл-черновик** `requirements-<case>.tmp.json` / `test-cases-<case>.tmp.md`. Это рабочие черновики для исключения конфликтов одновременной записи, НЕ постоянные артефакты. **Оркестратор на завершении шага сводит их в единый постоянный файл** (`requirements.json` / `test-cases.md` как актуальный срез набора) и **удаляет черновики**. Постоянное хранилище всегда — единый файл с актуальным срезом.

Правила:
1. **Продуцирующий агент обязан** заполнять `_meta`/`metadata` при записи артефакта (в актуальном срезе).
2. **Потребляющий агент** при чтении сверяет `schema_version` с ожидаемой и читает файл как актуальный срез (для `batch` учитывает все `case_keys`). При несовпадении — фиксирует предупреждение в журнал прогона и действует по своей самодостаточности (не тихо ломается и не выдумывает поля).
3. Смена структуры артефакта = инкремент `schema_version` и запись в `fix-history.md` (миграция).
4. **Совместимость с миграцией:** если при чтении встретился контейнер с `runs[]` (из промежуточной итерации схемы) — брать актуальный срез как `runs[-1]`; иначе файл читается как есть. Прошлые прогоны в артефакт не дописываем.

## 🏗️ Bootstrap: сборка структуры на пустом репозитории

**Bootstrap** — сборка рабочей тестовой структуры, когда в репозитории тестового контура **нет вовсе**. Выполняется строго **из шаблонов скилла** (`.gigacode/skills/api-test-generation/templates/`), а не «из головы».

### Владелец bootstrap

**Bootstrap выполняет ОРКЕСТРАТОР, и только он** (в шаге 1 «Инициализация структуры проекта», до запуска субагентов):
- Оркестратор один раз решает «тестовой структуры нет → собрать из `templates/`», создаёт каркас, и только потом запускает субагентов (с шага генерации теста).
- **Субагенты не конкурируют за bootstrap** и не собирают структуру в рамках пайплайна (иначе — гонки и дубли).
- **Исключение (изолированный запуск субагента):** если субагент (например `test-generator`) запущен **вне пайплайна**, без оркестратора, и структуры нет — он создаёт по шаблонам **только минимум, необходимый для конкретного тест-кейса** (нужный клиент, билдер, DTO, конфиг), а не полный каркас. Это fallback, а не второй канон.

### Условие применения

- **Только пустой контур.** Если тестовая структура уже существует (`conftest.py`, клиенты, `test_suites/`) — bootstrap **не выполняется**: сканируй факт, дополняй только недостающее для кейса, существующий код **не затирается** (принцип «структура есть → она рабочая», см. «🛠️ Определение `<test_root>`»).
- Структура может существовать «по другому пути» (например `e2e/tests/`) — тогда `<test_root>` берётся из неё (из `conftest.py`), bootstrap не нужен.

### Из чего собирается каркас (таблица «шаблон → файл»)

Оркестратор создаёт готовую рабочую структуру, копируя и адаптируя шаблоны:

| Шаблон в `templates/` | Куда кладётся (в `<test_root>` / корень) |
|---|---|
| `conftest_template.py` | `<test_root>/conftest.py` (контекст, фикстуры) |
| `http_client_template.py` | `<test_root>/rest/core/http_client.py` |
| `config_template.py` | `<test_root>/rest/config/configs.py` |
| `builder_template.py` | `<test_root>/rest/helpers/request_builders.py` |
| `client_template.py` | `<test_root>/rest/clients/<resource>.py` (по мере необходимости) |
| `model_template.py` | `<test_root>/rest/models/<dto>.py` (по мере необходимости) |
| `test_template.py` | `<test_root>/rest/test_suites/test_<feature>.py` (для кейса/по мере необходимости) |
| `pytest_config_template.ini` | корень → `pytest.ini` (или в `pyproject.toml`) |
| `gitignore_template.txt` | `.gitignore` |
| `README_template.md` | `<test_root>/README.md` |
| `env.example` | `.env.example` |

Итоговый каркас (`Just Enough Structure`, создаётся на этапе bootstrap, наполняется позже генератором):

```
<test_root>/
├── conftest.py                     ← фикстуры/контекст
├── requirements.txt                ← зависимости (pytest, requests, pydantic)
├── README.md
├── rest/
│   ├── core/http_client.py         ← базовый HTTP-клиент (адаптируется: URL, авторизация)
│   ├── clients/                    ← API-клиенты (заполняет generator по кейсу)
│   ├── models/                     ← Pydantic DTO (заполняет generator по кейсу)
│   ├── config/configs.py           ← конфиги
│   ├── helpers/                    ← билдеры (заполняет generator по кейсу)
│   └── test_suites/                ← тестовые файлы (из test_template.py)
```

**Принцип «Just Enough Structure»:** перед созданием каждого файла отвечай «нужен ли он для этого тест-кейса?». На bootstrap создаётся **каркас** (conftest, http_client, структура папок, конфиг), а клиенты/модели/билдеры/тест-файл под конкретный эндпоинт создаёт `test-generator` **по мере надобности**, а не все заранее.

**Адаптация шаблонов:** оркестратор копирует шаблон и подставляет проектное (базовый URL, авторизация, структура конфига) из шаблона/проекта — он **не** создаёт файлы «из головы», а применяет твои шаблоны из папки скилла.

## 📇 Машиночитаемый отчёт прогона

Каждый прогон пайплайна завершается генерацией **машиночитаемого отчёта** — единого
структурированного паспорта, который агрегирует шаги, статусы, метрики качества и результат
в один JSON. Журнал прогона — это человекочитаемая сводка **поверх** этого отчёта, а не отдельная
сущность: сводку можно формировать из отчёта.

### Файл отчёта (актуальный срез)

- **`.gigacode/design/report.json`** — **одна** фиксированная точка для CI и быстрой проверки. Хранит **актуальный срез** отчёта и **перезаписывается целиком** на каждый новый прогон. Отдельных файлов `report-<batch>-<timestamp>.json` и накопления истории `runs[]` **не** ведём.
- **Актуальный отчёт** — сам файл. Его читают CI/скрипты (парсинг статуса, вердикта гейта, длительности).
- Единичный кейс и набор пишут в один и тот же `report.json` целиком (для набора — `case_keys` и `results_per_case`).
- История прогонов — вне файла (git + `fix-history.md`).
- **Отчёт не хранит уроки.** `report.json` — паспорт текущего прогона: статус/вердикт/артефакты. Содержательный опыт (`lesson`/`type`/`cause`/итог блокера) живёт в `.gigacode/design/fix-history.md` (см. «💾 Опыт накопления»). Не оставляй блокер/замечание только в отчёте — продублируй его в `fix-history.md`, иначе при перезаписи отчёта урок потеряется.

### Человекочитаемый HTML-отчёт (обязательный)

Помимо машиночитаемого `report.json`, каждый прогон завершается обновлением **одного сводного HTML-отчёта на scope** — человекочитаемого вывода пайплайна. Отдельного отчёта на каждый прогон или группу нет.

- **Файл:** `.gigacode/design/test-report-<scope>.html`, по эталону `.gigacode/skills/api-test-generation/templates/report_template.html`.
- **Публикация:** через инструмент `artifact` (если он есть в окружении).
- **Вкладки:** Сводка, Тесты, Карта TC→AC, Эндпоинты, Метрики, Блокеры, Уроки.
- **Данные:** все артефакты `.gigacode/design/` (`report.json`, `quality-gate.json`, `test-cases.md`, `fix-history.md`) и код сьютов. Отчёт пересобирается целиком на каждом прогоне, поэтому отражает все покрытые кейсы, а не только последний. Цифры не хардкодятся.
- **Роль:** не заменяет `report.json` (источник для CI) и не является Allure-отчётом. Если шаблон не найден или генерация не удалась — пайплайн не блокируется, оператор видит предупреждение.

### Формат отчёта

Один и тот же **контракт отчёта** для одиночного кейса и набора. Файл `report.json` — единый актуальный документ вида `{ "_meta": {...}, "pipeline": {...}, "quality_gate": {...}, "result": {...} }`. В batch-режиме поля `case_key`, `test_file`,
`passed`, `failed` — массивы/суммы по набору тестовых сценариев; в single — скаляры.

```json
{
  "_meta": {
    "schema_version": "2.0",
    "case_key": ["<PROJECT_KEY>-TXXXX"] | "<PROJECT_KEY>-TXXXX",
    "generated_by": "orchestrator",
    "generated_at": "<ISO-8601>",
    "skill_version": "<версия скилла>"
  },
  "pipeline": {
    "status": "completed | blocked",
    "mode": "single | batch",
    "steps": [
      {
        "id": "matcher",
        "status": "pass | fail | skipped",
        "artifact": "code-patterns.json",
        "duration_sec": 12,
        "attempts": 1,
        "note": "..."
      }
    ],
    "blocker": null | {"agent": "...", "reason": "..."},
    "total_duration_sec": 123
  },
  "quality_gate": {
    "coverage_strategy": {"score": 0.9, "covered": 9, "total": 10, "verdict": "pass"},
    "code_quality": {"fidelity_score": 1.0, "cost_score": 0.8, "quality_score": 0.9, "threshold": 0.7, "verdict": "pass"},
    "external": {"external_rate": 0.0, "blocked": false}
  },
  "result": {
    "test_file": ["tests/.../test_a.py"] | "tests/.../test_a.py",
    "pytest_status": "passed | failed | blocked",
    "passed": 1,
    "failed": 0
  }
}
```

> **Allure-отчёт не входит в отчёт прогона.** Генерация/публикация Allure-отчёта и ссылка на него (`allure_report.url`) отключены и в `report.json` секции `allure_report` нет. Allure-декораторы/шаги в тестах остаются (часть структуры проекта), но шаг генерации отчёта не запускается.

**Источники секций:**
- `pipeline` — журнал прогона (шаги, время, попытки, блокер) — заполняет оркестратор.
- `quality_gate` — напрямую из `.gigacode/design/quality-gate.json` (см. раздел «📊 Метрики качества и пороговый гейт»).
- `result` — итог запуска теста (от валидатора).

**Связь двух разделов:** гейт качества (см. «📊 Метрики качества и пороговый гейт») — это *расчёт* метрик; отчёт (см. «📇 Машиночитаемый отчёт прогона») — это *сборка* их вместе с
шагами и результатом в единый паспорт. `quality-gate.json` остаётся отдельным производным
файлом, `report.json` (актуальный срез) его агрегирует — не дубль, а единая точка чтения.

**Кто отвечает за генерацию:** `report.json` (перезапись актуальным срезом) собирает **оркестратор** на
шаге `report` (Step 8) из журнала прогона + `quality-gate.json` (актуальный срез) + результата валидации.

**Потребители:** CI/скрипты (парсинг статуса, вердикта гейта, длительности), сравнение прогонов
между наборами тестовых сценариев, объективный паспорт прогона при ревью/публикации скилла.

## 💾 Сохранность опыта (`fix-history.md`) — обязанность оркестратора

**Правило разнесения:** любой **урок/блокер** прогона (external/codable/fidelity, cause, lesson, итог) должен жить в `fix-history.md` и **не может оставаться только в `report.json`**. Наличие/статус текущего прогона отражается в `report.json`, а **содержательный опыт — в `fix-history.md`**. Если по какому-то прогону в `report.json` есть блокер/замечание, но в `fix-history.md` записи нет — это признак потери урока, и оркестратор обязан её устранить (см. «гарантированная сохранность опыта» ниже).

**Основной писатель записей — `test-validator`**, а остальные агенты базу только ЧИТАЮТ (не изменяют). Однако инструменты валидатора (write/shell) могут быть недоступны в конкретном окружении — поэтому действует правило **гарантированной сохранности опыта**:

- Если `test-validator` может писать — он сохраняет запись сам.
- Если НЕ может (нет write/shell) — он ОБЯЗАН подготовить **готовый текст структурной записи** (в рамках формата ниже) и вернуть его оркестратору дословно в отчёте.
- **Оркестратор ОБЯЗАН обеспечить попадание этой записи в `.gigacode/design/fix-history.md`** (записать сам по переданному тексту либо проконтролировать, что валидатор сохранил). Утрата урока из-за «незаписалось» — недопустима.

Это критично для самообучения скилла: без персистентности в `fix-history.md` прогон не «обучается», и следующие прогоны повторяют прежние сбои.

## 🤖 Оркестратор и субагенты: обязанность запуска

**Субагенты существуют для выполнения своей работы — их надо вызывать, а не обходить.**
Оркестратор обязан инициировать вызовы субагентов **сам, автоматически, без ожидания
указания оператора** — в следующих случаях:

1. **Генерация тестов** (`test-generator`) — на основании артефактов
   `requirements.json`/`test-cases.md`/`code-patterns.json` и контура.
2. **Правки после генерации** (`test-fixer`) — любое изменение уже сгенерированного
   тестового кода выполняется НЕ оркестратором напрямую, а через `test-fixer`.
3. **Валидация / итерации** (`test-reviewer`, `test-validator`) — ревью и запуск/анализ
   теста тоже выполняют соответствующие субагенты.

**Правила:**
- Оркестратор **не пишет и не правит тест-код сам**, если для этого есть субагент
  (generator / fixer). Он вызывает агентов и передаёт им контекст.
- Если оператор не попросил «запусти субагентов» — это НЕ означает, что их можно
  не вызывать. Обязательность запуска не зависит от подсказки пользователя.
- Исключение — **инфраструктура контура** (скелет: `core/`, `clients/`, `models/`,
  `utils/`, `conftest.py`) на пустом репозитории: её собирает оркестратор из шаблонов
  (`templates/`), т.к. шаблоны подготовлены именно для оркестратора. Субагенты
  подключаются **начиная с шага генерации теста** (и далее их правки).
- При любом сомнении, что работа — это «генеративная/правка теста», следует
  передать её соответствующему субагенту, а не выполнять самому.

### 🚀 Автономность оркестратора (без запроса подтверждения команд)

Пайплайн самодостаточен: **оператор не подтверждает отдельные команды внутри прогона**
(«кинул кейс → через 10 минут готово»). Это не расширение прав, а правило распределения
команд и ролей. Пункты (дополняют раздел «🛡️ Права агентов и автономность» выше):

1. **Командные шаги выполняют субагенты** (см. их профиль `tools:`): pytest запускает
   `test-validator`, код правит `test-fixer`/`test-generator`, артефакты пишут продуцирующие
   агенты. Оркестратор по умолчанию **не выполняет** эти команды сам — это убирает
   лишние запросы подтверждения (при исполнении команды не субагентом возникает
   подтверждение у оператора).
2. **Субагенты шагов пайплайна запускай ТОЛЬКО в фоне (`run_in_background: true`).**
   Синхронный запуск (`run_in_background: false`) переводит субагентов в интерактивный
   режим: их `run_shell_command` ждёт подтверждение оператора и останавливает прогон на
   каждом `ask`. Фоновый запуск (по умолчанию для top-level субагентов) применяет
   `permissions.allow` без интерактивного ожидания — это гарантия автономии у оператора и
   у всех, кто скопирует скилл, независимо от их `settings.json`. Ожидание завершения
   фонового шага — строго по `task-notification`, продолжение — по фактическому состоянию
   артефактов, без таймеров/будильников.
3. Если субагент по техническим причинам не может выполнить команду (нет shell/инструмента),
   он возвращает **готовую команду в отчёте**, а оркестратор исполняет её **без запроса
   подтверждения у оператора** — это внутренний шаг пайплайна, а не «действие по требованию
   оператора».
4. Оркестратор **не обращается к оператору за разрешением** на: запуск pytest, правку
   файлов кода/артефактов `.gigacode/design/`, обновление `fix-history.md`/`quality-gate.json`/
   `report.json`, чтение/перезапись артефактов, работу с git в рамках прогона. Это внутренние
   шаги скилла.
5. **Единственное обращение к оператору** — нехватка входных данных, невыводимых из
   кейса/проекта (внешний блокер: стенд 403 с просьбой валидного `authToken`/`sessionToken`/токена,
   отсутствие данных, неоднозначность, требующая решения оператора, решение «перезапустить
   ли валидатор»). Это **запрос недостающих данных**, а не «разрешение на команду»; он
   обязателен и автономностью не отменяется (см. «⏸️ Персистентность внешнего блокера»).
6. Оркестратор обязан различать два случая: «запрос на выполнение команды» — **никогда не
   выдаётся оператору**; «запрос недостающих входных данных» — **обязательно выдаётся** при
   внешнем блокере/неоднозначности. Смешение этих случаев — ошибка оркестратора.
7. Права согласованы с автономной моделью: суб-агенты обладают `run_shell_command`/`edit`
   (см. «🛡️ Права агентов и автономность»), а автономность обеспечивается маршрутизацией
   команд в субагенты и фоновым запуском шагов + `approvalMode: auto-edit`. Глобальные
   настройки допустимы; при рассинхроне прав профили приводятся к таблице прав агентов.
