# Онбординг: передача скилла `api-test-generation` в другую команду

Этот документ — инструкция для **тех, кто подключает скилл в новом репозитории/команде**.
Он про то, что сделать один раз перед первым прогоном и что скилл сделает сам.
Конечному пользователю (QA), который просто генерирует тесты, читать это не обязательно —
ему достаточно `README.md`.

> Принцип: **скилл самодостаточен.** Он сам анализирует структуру проекта, сам выводит
> `<test_root>`, `base_url`, схему авторизации и паттерны из вашего кода. Вам не нужно
> переписывать конфигурацию под свой проект — нужно лишь обеспечить условия запуска.

---

## 1. Что перенести в новый репозиторий

Скилл живёт в папке .gigacode. Переносите как единый комплект:

```
.gigacode/skills/api-test-generation/     # сам скилл (SKILL.md, README.md, templates/)
.gigacode/agents/                         # 7 субагентов пайплайна
.gigacode/design/common-principles.md     # ядро правил пайплайна
.gigacode/tools                           # инструменты
.gigacode/GIGACODE.md                     # Инструкция для агента
.gigacode/settings.json                   # Настройки mcp, права агента
```

Остальное в `.gigacode/design/` (`code-patterns.json`, `requirements.json`, `test-cases.md`,
`report.json`, `quality-gate.json`, `fix-history.md`) — это **артефакты прогонов**, а не часть
скилла. На новом проекте они будут созданы заново при первом прогоне. Если переносите
накопленный опыт — можно взять только `fix-history.md` (базу знаний), но это опционально.

Если в новом проекте тестового контура **ещё нет** — скилл собирает его сам из `templates/`
(bootstrap, см. `SKILL.md` → «🏗️ Bootstrap»). Ничего вручную создавать не нужно.

## 2. Что подготовить ДО первого прогона

Скилл сам разберётся с контуром, но **без этих предметов он не сможет прогнать тест**:

| Что | Зачем | Кто делает |
|---|---|---|
| **Репозиторий на Python + pytest** | Скилл генерирует и запускает pytest-тесты | вы |
| **Доступный стенд/окружение** | Фактический прогон теста, реальные ответы 2xx/4xx/5xx | вы (сеть, URL, доступ) |
| **Данные для авторизации** | Токены/ключи/сертификаты, если API за auth | вы (стенд/токены) |
| **Зависимости** (`requests`, `pydantic`, `allure-pytest`, `pytest`) | импорт и запуск сгенерированного кода | вы (`requirements.txt`) |

Всё **остальное скилл определяет сам** автоматически на первом прогоне:

- `<test_root>` — по каноническому алгоритму из структуры проекта;
- `base_url`, фикстуры, пользователи, заголовки — из `conftest.py` и существующих тестов
  (агент `code-pattern-matcher`);
- модель требований, паттерны, стиль — из вашего реального кода через `requirements-analyst`
  и `test-case-designer`.

## 3. Важно: НЕ настраивайте вручную то, что выводится

Поскольку контур определяется субагентами на каждом прогоне, **не правьте** руками:

- `base_url` / стенд — если в старом проекте он был зашит в `conftest.py`, в новом матчер
  снимет актуальный URL из вашего `conftest.py`/конфига. Другой стенд = другой URL в контуре,
  скилл это увидит сам.
- Схему авторизации — если у вас `Bearer` вместо `x-user-id`/`x-session-id`/`x-client-id`,
  субагенты зафиксируют ваш реальный механизм из кода. Не надо «переписывать» скилл под auth.

Если вы всё же заметили, что кэш паттернов (`code-patterns.json`) устарел — удалите его,
матчер пересканирует контур (правило управления кэшем в `SKILL.md` / `code-pattern-matcher.md`).

## 4. После переноса — проверочный прогон

1. Убедитесь, что скилл и агенты видны (команда `/skills`, либо вызов скилла по имени).
2. Отправьте скиллу **один простой ввод** — лучший вариант тест-кейс или Swagger на один
   известный вам эндпоинт.
3. Проверьте, что:
    - пайплайн прошёл 7 шагов (matcher → … → validator) без остановки на «разрешите команду»;
    - итог — сводка в `report.json`, тест-файл в `<test_root>/test_suites/`, запись в `runs.jsonl`
      и **накопительный дашборд** `test-report.html`, собранный скриптом `tools/report_tool`;
    - паузы (если были) — только по недостающим данным/решению, а не по подтверждению команд.

> **Передача контекста между субагентами — только через файлы-артефакты и промпты вызова.**
> Пайплайн **не использует** `send_message` для шагов: субагенты работают последовательно и
> обмениваются данными через файлы на диске. Оркестратор проверяет, что артефакт шага реально
> создан, прежде чем запускать следующий; если субагент завершился без записи файла — он
> перезапускается новым вызовом (без `send_message`). Это часть автономности пайплайна
> (правило — в `SKILL.md` → «Запуск агентов и передача контекста»).

## 5. Jira/Zephyr (трассировка)

- Скилл **не требует** Zephyr для генерации: тест-кейсы можно дать ссылкой Swagger или
  копией текста.
- Если новая команда хочет трассировку в свой Zephyr — сгенерируйте по своим реальным кейсам
  и проставьте их ключи. Синтетические/чужые ключи не ставьте (по правилу проекта).
- Настройка Zephyr-проекта/маркеров — на стороне команды, скилл лишь навешивает маркер
  с переданного ключа.

## 6. Чек-лист готовности к передаче

- [ ] Скилл скопирован в репозиторий команды
- [ ] `requirements.txt` установлены (pytest, requests, pydantic, allure-pytest)
- [ ] Есть стенд + доступ/токены для реального прогона
- [ ] Проверочный прогон на 1 эндпоинте дал итог в `report.json`
- [ ] Пайплайн не запрашивал подтверждений команд (только данные/решения)
- [ ] Команда ознакомлена с `README.md` (что умеет / как генерировать / когда скилл спросит)

## 7. Ограничения, чтобы не было ложных ожиданий

- Скилл рассчитан на **Python + pytest**. Другой язык/раннер не поддержан.
- Для прогона нужен **фактический доступ к стенду**. Без стенда сгенерировать можно, но
  валидация/зелёный прогон невозможны.
- Скилл **не перетирает** существующие тесты — только дописывает новое.
- Публикация Allure-отчёта (HTML) отключена; результат — `report.json` и журнал в терминале
    + **накопительный HTML-дашборд** по всем прогонам (собирает `tools/report_tool`, не Allure).
- Для полной автономности пайплайн передаёт контекст между субагентами **только через файлы**
  и верифицирует запись артефакта после каждого шага; внутреннее подтверждение команд/шагов
  не запрашивается (см. п.4).
