# GigaCode Rules

## 🚀 Как сгенерировать автотест по тест-кейсу Jira/Zephyr

### Быстрый старт

Скинь ссылку на тест-кейс в формате:

```
Сгенерируй автотест по кейсу: https://jira.sberbank.ru/secure/Tests.jspa#/testCase/<PROJECT_KEY>-TXXXX
```

Агент пройдёт полный пайплайн через 7 под-агентов:

```
code-pattern-matcher → requirements-analyst → test-case-designer → test-generator → test-reviewer → test-fixer → test-validator
```

Итог: готовый автотест в `<test_suites>/test_<feature>.py` (каталог сьютов контура, см. `common-principles.md` → «🛠️ Определение `<test_root>`») + машиночитаемая сводка прогона (`report.json`). Пайплайн выполняется автономно (без ручных подтверждений между шагами); оркестратор сам запускает команды `pytest` на шаге валидации. Генерация и публикация Allure-отчёта отключены.

### Правило размещения тестов в файле (`test_suites/`)

- **Один эндпоинт → один файл.** Все тест-кейсы на один и тот же целевой эндпоинт собираются в **одном** файле `test_<feature>.py` (имя по смыслу проверки, не привязано к какому-либо конкретному имени вида `test_<resource>.py`), независимо от их количества.
  - Нет файла под эндпоинт → создай новый.
  - Уже есть файл/тесты для этого эндпоинта → дописывай новые кейсы в **тот же** файл.
  - Это касается и ситуаций, когда разные тест-кейсы (2-й, 3-й и т.д.) дергают один и тот же эндпоинт — для каждого **не** создаётся отдельный файл.
- **Новый эндпоинт → новый файл.** Кейс на другой эндпоинт размещается в отдельном файле.
- **Запрещено затирать и редактировать существующие тесты.** При работе в существующем файле НЕ изменяй, НЕ переписывай и НЕ удаляй уже написанные тест-методы/классы/фикстуры/константы — только добавляешь свой новый тест рядом (не дублируя уже существующие в нём функции/константы).

### Как сгенерировать тест по Swagger/OpenAPI

Скинь ссылку на Swagger-документацию:

```
Сгенерируй автотесты по Swagger: https://petstore3.swagger.io/api/v3/openapi.json
```

Агент:
1. Запустит парсинг через `openapi_tool`
2. Создаст Pydantic-модели из спецификации
3. Сгенерирует тесты с использованием этих моделей

## ⚠️ Автономный режим (по умолчанию)

Пайплайн работает **полностью автономно**: все команды (`python -m pytest`, `openapi_tool`, `git` и любые прочие), правки файлов и внутренние операции между под-агентами выполняются **без запроса разрешения у пользователя**. Не прерывай работу вопросами вида «можно выполнить команду?» / «продолжать?» на каждом шаге.

**Обращайся к пользователю ТОЛЬКО при внешнем блокере**, который невозможно преодолеть кодом/автономно:
- не хватает входных данных (нет тела запроса, параметров, URL, тест-кейса);
- нет доступа к стенду/окружению / сервис стабильно отвечает 4xx/5xx из-за данных;
- неясность требования, которую нельзя вывести из кода/контура;
- исчерпаны лимиты самоисправлений (max 4 итерации у `test-validator`, цикл ревью ≤ 4) без результата.

В этих случаях останавливайся и запрашивай только недостающее/решение, продолжая с того же агента (см. `continue_from` в SKILL).

## 🔒 Правило Test Case Fidelity

**КАЖДЫЙ шаг тест-кейса → КАЖДЫЙ Allure-шаг, КАЖДЫЙ expected_result → КАЖДАЯ проверка.**

Никогда не добавляй проверки, которых нет в тест-кейсе — даже если "очевидно нужны".

## 🧩 Самодостаточность и доставка правил

Система агентов **самодостаточна, самостоятельна и универсальна в рамках Python-контура** (pytest/Allure/Jira-Zephyr): она работает в любом Python-проекте/команде, даже при пустом `.gigacode/design/`, где гарантированно присутствует только `.gigacode/design/common-principles.md`. Профильная специализация — Python/pytest: структура тестового дерева, маркеры и ключ Jira-проекта адаптируются автоматически.

Обязательства:
1. **`common-principles.md` всегда доставляется агенту.** Перед запуском любого под-агента убедись, что файл `.gigacode/design/common-principles.md` доступен (он — постоянный источник всех правил качества: Test Case Fidelity, критерии, «чего НЕ делать», классификация ошибок). Это **постоянный** файл контура, не нагенерированный; в норме присутствует всегда (статусы файлов — см. `common-principles.md` → «📂 Статус файлов»). Если файла нет — это **аномалия** (повреждение контура скилла): агент работает по критичным правилам, зашитым в промпт (Test Case Fidelity, классификация причин, границы ролей), а ты извещаешь оператора о необходимости восстановить ядро.
2. **`code-patterns.json` — кэш-оптимизация, не обязательная зависимость.** Пайплайн должен отработать по любому тест-кейсу даже без этого файла: каждый агент умеет самостоятельно определить контур (найти `conftest.py`, фикстуры, клиенты, билдеры, паттерны) по протоколу «Определение контура» в своих промптах.
3. **Никаких дословных дублей правил.** Правила живут только в `common-principles.md`; промпты и SKILL ссылаются на него, а не копируют.

## ✅ После генерации автотеста

В автономном режиме запуск сгенерированного теста `test_<name>` выполняется **автоматически** (шаг валидации через `pytest`). Не спрашивай разрешения на запуск.

Спрашивать пользователя не нужно; вместо этого продолжай пайплайн до финального отчёта (`report.json` + HTML-отчёт). Обращение к пользователю — только при внешнем блокере (см. «⚠️ Автономный режим»).
