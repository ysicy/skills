# Общие принципы тестовой автоматизации

Этот файл читают **все** агенты пайплайна. Здесь только правила, общие для всех ролей.
Правила конкретной роли — в файле агента (`.gigacode/agents/<agent>.md`),
правила оркестратора — в `.gigacode/skills/SKILL.md`.

## 🖥️ Формы shell-команд (для всех агентов с `run_shell_command`)

**Практическое правило выбора форм команд (снижающее подтверждения).** Субагент обязан выбирать такие формы `run_shell_command`, которые с меньшей вероятностью уходят в `ask`, и работать через параметр `directory` инструмента, а не через `cd`:

- ✅ ПРЕДПОЧТИТЕЛЬНО (уходят по узким allow-правилам): `python -m pytest …` / `python -m py_compile …` / `python -c "…"` / `git …` / `ruff …` — из корня проекта (root), **без** `cd` в путь вне проекта; рабочую директорию задавай параметром `directory` (корень проекта).
- ❌ ИЗБЕГАЙ (провоцируют ask/deny у хоста): `cd /home/... && …` (абсолютный путь через cd), heredoc (`cat > file <<'EOF'`), `rm -rf`/`rm -f`, `cat`/`tail` файлов **вне** workspace (например `~/.gigacode/settings.json`), `find ... -path '*allure*' -mtime` (нет в allow). Заменяй их инструментами `read_file`/`glob`/`write_file`/`edit` или `python`-однострочниками из корня проекта.
- Если первая форма команды отклонена (deny) — это НЕ подтверждение и НЕ блокер: в пределах итерации тут же пробуй эквивалент из списка ✅ выше и НЕ останавливайся для запроса оператора.
- `rm` временных файлов делай только через `python -c "import os; os.remove(...)"` из корня проекта.

## 🛠️ Определение `<test_root>` (единый алгоритм)

`<test_root>` — корень тестового дерева. Определяется **один раз в начале пайплайна** и передаётся всем агентам; все относительные пути агентов считаются от него. Скилл **универсален** и не завязывается на конкретную структуру — корень выводится из фактической структуры проекта, а схема папок не навязывается.

**Каноническая последовательность (первый успешный шаг = результат):**
1. **Явный путь оператора.** Если оператор передал путь к тестовому каталогу — используй его.
2. **`conftest.py`.** Найди `conftest.py`, сканируя от корня репозитория вверх/вглубь (до 3 уровней). `<test_root>` = каталог с ним.
3. **`pytest.ini` / `pyproject.toml`.** Найди файл конфигурации pytest. `<test_root>` = каталог с ним, если в нём есть тесты; иначе — `tests/` рядом.
4. **`requirements.txt` + `tests/`.** Если в корне есть `requirements.txt` и рядом каталог `tests/` — `<test_root> = tests/`.
5. **Подсказка из кэша (не источник).** Если `.gigacode/design/code-patterns.json` содержит `project_context.test_root` — учитывай как подсказку, но источник истины — фактическая структура (шаги 1-4). Не подчиняйся кэшу, если он расходится с фактом.
6. **Дефолт.** Ничего не найдено → `<test_root> = "tests"`.

**Принцип «структура есть → она рабочая»:** если тестовый каталог существует — **не придумывай и не навязывай** собственную схему папок (`tests/rest/...` и т.п.). Используй фактическую структуру как есть; дополняй только то, чего не хватает для конкретного тест-кейса, не перестраивая существующее (см. «Чего НЕ делать» и `skills/SKILL.md` → «🏗️ Bootstrap»).

**Принцип «пустого репозитория»:** если тестовой структуры **нет вовсе** — не останавливайся с пустыми руками и не выдумывай пути вручную: оркестратор собирает полную рабочую структуру **из шаблонов скилла** (`templates/`) по канону `skills/SKILL.md` → **«🏗️ Bootstrap: сборка структуры на пустом репозитории»**, а `<test_root>` создаётся как корень этих шаблонов. Шаблоны применяются **только** на пустом контуре; на непустом — существующий код не затирается.

**Каталог тест-файлов `<test_suites>`** — где лежат тест-файлы. Определяется вместе с `<test_root>`:
1. по `code-patterns.json` → `project_context.test_path_pattern` (каталог, где фактически лежат существующие `test_*.py`);
2. если тестов ещё нет и контур собран bootstrap'ом — `<test_root>/rest/test_suites`;
3. иначе — `<test_root>`.
Все агенты пишут и запускают тест по пути `<test_suites>/test_<feature>.py`.

**Консистентность:** все агенты используют один и тот же `<test_root>`, передаваемый оркестратором. Никакой агент не переопределяет корень по-своему; при расхождении — авторитетен алгоритм из этого раздела.

## 🧠 Принципы разработки

Каждый агент в пайплайне обязан придерживаться этих принципов:

1. **Трассируемость** — каждый тест должен ссылаться на конкретное требование/кейс/эндпоинт/acceptance criterion. Цепочка: требование → тест-кейс → код → результат.
    - **Один тест-кейс → ОДИН тест-метод.** Тест-кейс из N шагов — это **один** автотест, внутри которого шаги оформляются как последовательные `with allure.step(...)`, а проверки — в порядке кейса. НЕ дробить один кейс на N тестов по числу шагов/acceptance criteria: это рвёт трассировку кейс→тест и множит сущности без нужды. Атомарность (п.3) применяется к шагам/проверкам **внутри** кейса, а не к делению кейса на тесты.
2. **Идемпотентность** — повторный запуск теста не меняет состояние системы. Тест не должен зависеть от предыдущих запусков.
3. **Атомарность** — тест независим от других тестов в наборе. Один шаг кейса → одна проверка (в рамках метода). «Атомарной единицей» является шаг/проверка, а не тест-кейс: кейс с несколькими шагами сохраняет все шаги в одном методе.
4. **Самодостаточность** — тест не полагается на внешние данные (кроме фикстур). Все данные или из фикстур, из конфигов, или из билдеров.
5. **Понятность для человека** — код читается как документация, даже без комментариев.
6. **Переиспользуемые фикстуры — только в `conftest.py`.** Фикстуры API-клиентов и данные, переиспользуемые несколькими сьютами (например фикстуры аутентифицированного пользователя, готовых API-клиентов ресурсов и т.п.), определяются **только в `<test_root>/conftest.py`**, рядом с существующими, в едином стиле. В тест-файле (`test_*.py`) **запрещено** заново определять такие фикстуры — это дублирование и рассинхрон с общим контуром. Тест-файл их только ИСПОЛЬЗУЕТ по имени. Исключение — тест-локальная фикстура/вспомогательная функция, нужная исключительно одному сьюту и не существующая в контуре: тогда она либо выносится в `conftest.py`/helpers, либо оправданно остаётся в тест-файле (по решению с учётом принципа «структура есть → она рабочая»). Клиент/модель/билдер под ресурс — всегда в выделенных каталогах (клиенты/модели/хелперы тестового дерева), никогда не в тест-файле.

## 🚫 Чего НЕ делать (общие правила для всех агентов)

- Не генерировать тесты без анализа требований
- Не создавать новые модели/фикстуры, если есть готовые в `code-patterns.json`
- Не игнорировать существующие паттерны проекта
- Не выдавать код без проверки на работоспособность
- Не оставлять TODOs и заглушки без объяснения
- Не начинать генерацию, пока не получен конкретный тест-кейс или путь к нему
- Не пытаться ходить по ссылке, если MCP Jira не настроен — просто попроси скопировать шаги
- Не додумывать шаги, если они неполные — запроси уточнение у пользователя
- Не исправлять код, если не понятна проблема — запроси уточнение
- Не переписывать тест полностью — только точечные правки
- Не добавлять новые сценарии (это задача test-generator)
- Не менять архитектуру теста без согласования
- При выдаче **внешнего блокера** (стенд недоступен, 4xx/5xx из-за данных, не хватает входных) — фиксировать его в постоянном артефакте (`.gigacode/design/fix-history.md` или отдельный файл), а не только в чате: оркестратор обязан пережить паузу и сохранить причину между перезапусками агентов

## 🏷️ Маркеры интеграции со статусами (fail/pass, автологические отчёты)

Интеграция проставления статусов теста (pass/fail) для автоматического формирования отчёта может быть реализована по-разному: разных механизмов (pytest-маркер, allure-метка, и др.). **Название маркера или иного механизма — не фиксировано и зависит от конкретного окружения.**

**Правило для всех генеративных и правящих агентов (designer, generator, fixer, reviewer):**
1. **Не хардкодь название маркера** (например `zephyr`, `jira`, `test_case_key` и т.п.) как жёсткую константу — ни в `common-principles.md`, ни в промптах, ни в сгенерированном коде.
2. **Маркер/механизм берётся из фактической структуры проекта:** агент считывает, какой именно механизм использует текущий контур (`conftest.py`, существующие тесты в `test_suites/`, `pytest.ini`, `code-patterns.json` → `allure_patterns.decorators`). В одном окружении это может быть `zephyr`, в другом — иной маркер или другой подход.
3. Если в текущем контуре **есть** рабочий механизм проставления статусов — генератор проставляет в новых тестах аналогичный (чтобы не ломать автоматический отчёт).
4. Если такого механизма в проекте **нет** — генератор НЕ придумывает и НЕ проставляет маркер, оставляет новый тест без него.
5. **Не удаляй и не переименовывай** существующий маркер у уже написанных тестов — это может сломать автоотчёт. Изменение маркеров — только осознанно, под контролем оператора.
6. Не «переноси» маркер из другого проекта/окружения — следуй только тому механизму, который реально присутствует в текущей структуре.

> Пример: в проекте A интеграция через `@pytest.mark.zephyr("<CASE_KEY>")` → генератор ставит этот маркер. В проекте B интеграции нет или другой механизм → генератор ничего не ставит или ставит найденный в структуре аналог.

Данный раздел читают: **test-generator**, **test-fixer**, **test-case-designer**, **test-reviewer**, **code-pattern-matcher** (решает в `code-patterns.json` поля `allure_patterns.decorators`).

## 🔒 Test Case Fidelity (Точность по тест-кейсу)

**Когда источник — тест-кейс из Jira (Zephyr), а не OpenAPI или требования:**

1. **НЕ ДОДУМЫВАЙ** шаги, проверки, предусловия — строго только то, что в тест-кейсе.
2. **КАЖДЫЙ шаг → КАЖДЫЙ Allure-шаг, КАЖДЫЙ expected_result → КАЖДАЯ проверка.** 1-в-1 перевод.
3. **НЕ ДОБАВЛЯЙ** проверки, которые "кажутся логичными". Пример: тест-кейс проверяет только статус заказа → не проверяй `created_at`, `items`, `total` — их нет в ожидаемом результате, даже если они есть в примере ответа.
4. **НЕ ИНТЕРПРЕТИРУЙ** пример JSON-ответа из тест-кейса как инструкцию проверять каждое поле.
5. **ЕСЛИ тест-кейс неполный** — запроси уточнение у пользователя, НЕ заполняй пробелы.
6. **Невыводимость сценария = внешний блокер.** Если сценарий/проверка/приоритет (P0-P3) не выводится из тест-кейса или требований — это **внешняя причина**, а не повод «задокументировать assumption». Не добавляй такой сценарий с пометкой «предполагается»: остановись, зафиксируй блокер (см. `skills/SKILL.md` → «⏸️ Персистентность внешнего блокера») и запроси у оператора недостающее (полный список шагов/статус-кодов/правил). Не превращай API-контракт, бизнес-правило или «допущение» в проверки, которых нет в тест-кейсе.
7. **Применение к приоритетам.** Приоритеты P0-P3 — это способ *упорядочить* сценарии, которые реально есть в тест-кейсе/требованиях, а НЕ лицензия придумывать новые. Не выдумывай сценарий под каждую приоритетную категорию; строй только те, что выводятся из источника.
8. **Расхождение «кейс vs контур» — сигнал для оператора, а НЕ тихий «не блокер».** Если в тест-кейсе явно указано значение параметра/заголовка/данного (например конкретный заголовок авторизации, `id` сущности, значение поля), которое **конфликтует с фактическим контуром** (тестовые фикстуры, конфиги, DTO-клиент), это **внешняя неоднозначность источника**, а не «известное допущение».
    - Агент, обнаруживший конфликт (`requirements-analyst`, `test-case-designer`, `test-generator`, `test-reviewer`), обязан: зафиксировать его в артефакте (constraint `CN-xx` / примечание) **И** вернуть оркестратору явный маркер `requires_operator_input` с описанием конфликта (значение в кейсе vs значение в контуре).
    - **Оркестратор по маркеру `requires_operator_input` ОСТАНАВЛИВАЕТ пайплайн** до перехода к генерации/валидации и задаёт оператору вопрос через `ask_user_question`: «в кейсе <X>, контур даёт <Y> — это опечатка в кейсе, или нужно привести контур под <X>?». Решение оператора определяет дальнейшие действия:
        - если это **опечатка в кейсе / верно значение контура** — фиксируем решение в `review-report.md`/`fix-history.md` и продолжаем с контурным значением (тест не меняется);
        - если **нужно значение из кейса** — правка контура (добавить/параметризовать фикстуру, конфиг) силами `test-generator`/`test-fixer` или оркестратора, после чего продолжить.
    - **Запрещено молча принимать** контурный вариант и уходить в зелёный прогон, если в кейсе явное другое значение, а оператор не подтвердил.
    - Основание: неоднозначность, которую нельзя вывести из кейса, — внешний блокер по правилам `skills/SKILL.md` → «⏸️ Персистентность внешнего блокера» и «Test Case Fidelity», п.5-6. Тихий обход ведёт к тесту, который проверяет не то, что задумано в кейсе.

9. **Технический guard — не новая проверка.** Если проверка из кейса обращается к объекту, который может отсутствовать (`order.status` при `order is None`, поле последнего события потока, которого может не быть), перед ней в **том же** шаге допустим `assert <объект> is not None, "<сообщение>"`. Он не добавляет нового ожидания, а превращает `AttributeError` в понятное падение. Отдельным шагом или «на всякий случай» в начале теста guard не ставится.
10. **Шаг, закрытый фикстурой контура.** Если шаг кейса — подготовка (создать сущность, получить токен, подготовить данные), а в контуре есть фикстура, которая делает ровно это и падает при неуспехе, шаг закрывается фикстурой; повторять запрос и его проверку в теле теста не нужно.
11. **Шаг вне API.** Если шаг кейса проверяет состояние, недоступное через API/контур (настройка в админке, запись в БД без клиента), — не выдумывай способ проверки. Если в контуре есть клиент/фикстура для этого — используй её; если нет — считай шаг предусловием окружения, не включай его в код и укажи это в отчёте шага (что именно не автоматизировано и почему).
12. **Где проверять — по смыслу, а не по подстроке.** Ожидаемый результат проверяется по тому полю или событию ответа, которое **фиксирует именно этот факт**, а не поиском значения по всему тексту ответа: одно и то же значение может встречаться в ответе в разных ролях (в списке доступных вариантов, в эхо запроса, в справочнике), и только одно из мест означает проверяемый факт. Это вдвойне важно для отрицательных ожиданий («X нет», «Y не произошло»): отсутствие подстроки не доказывает отсутствия факта. Как в проекте принято проверять типовые факты — берётся из `code-patterns.json` → `domain_checks` (их снимает матчер с существующих тестов). Если из кейса и контура нельзя понять, какое поле фиксирует проверяемый факт, — это `requires_operator_input`, а не догадка.
13. **Пример ответа противоречит ожидаемому результату** (другое значение ключевого поля, нет нужного поля, пример обрезан или взят от другого запроса) — побеждает текст ожидаемого результата; пример используется только для понимания формата. Явное противоречие (значение в цели/шаге ≠ значению в примере) фиксируется в отчёте шага как замечание к кейсу.
14. **Негативный кейс без отличия от позитивного.** Если кейс заявляет условие (другая роль или пользователь, невалидные данные, несуществующая сущность), а входные данные не отличаются от позитивного варианта того же сценария, — это `requires_operator_input`: тест в таком виде не проверяет заявленное.

**Это правило приоритетнее всех остальных.** Даже если проверка "очевидно нужна" — если её нет в тест-кейсе, она НЕ ДОЛЖНА попасть в тест.

Этот раздел читают агенты: **test-case-designer**, **test-generator**, **test-reviewer**, **test-fixer**.
