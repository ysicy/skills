# Общие правила для всех агентов

Правила своей роли агент находит в конце своего файла (`.gigacode/agents/<agent>.md`), правила оркестратора — в `.gigacode/skills/api-test-generation/SKILL.md`.

## 🔒 Test Case Fidelity — главное правило

Действует, когда источник — тест-кейс (Jira/Zephyr или текст шагов). При конфликте с любым другим правилом побеждает оно.

1. Тест содержит только то, что есть в кейсе: шаги, проверки, предусловия. Ничего не додумывай.
2. Каждый шаг кейса — свой `with allure.step(...)`, каждый ожидаемый результат — своя проверка, в порядке кейса (исключения — п.10 и п.11).
3. Не добавляй проверок, которые «кажутся логичными». Кейс проверяет только статус заказа — не проверяй `created_at`, `items`, `total`, даже если они есть в примере ответа.
4. Пример ответа в кейсе показывает формат, а не список проверок.
5. Кейс неполный — запроси недостающее у оператора, не заполняй пробелы.
6. Сценарий, проверка или приоритет не выводится из кейса или требований — это внешний блокер. Не добавляй его с пометкой «предполагается» и не превращай API-контракт или бизнес-правило в проверку: остановись и верни блокер оркестратору.
7. Приоритеты P0–P3 упорядочивают то, что есть в источнике, и не обязывают придумывать сценарии под каждый приоритет.
8. **Кейс противоречит контуру.** В кейсе явно указано значение (заголовок, `id`, поле), а фикстуры/конфиги/клиент дают другое. Агент, заметивший это (analyst, designer, generator, reviewer), записывает конфликт в свой артефакт (constraint `CN-xx` или примечание) и возвращает оркестратору маркер `requires_operator_input`: «в кейсе X, контур даёт Y». Оркестратор останавливает пайплайн до генерации и спрашивает оператора:
   - опечатка в кейсе, верно значение контура → решение записывается в `review-report.md`/`fix-history.md`, продолжаем с контурным значением;
   - нужно значение из кейса → generator/fixer (или оркестратор) правит контур (фикстура, конфиг, параметризация), затем продолжаем.

   Молча принять значение контура и уйти в зелёный прогон нельзя.
9. **Технический guard — не новая проверка.** Если проверка из кейса обращается к объекту, которого может не быть (`order.status` при `order is None`), перед ней в том же шаге допустим `assert <объект> is not None, "<сообщение>"`. Отдельным шагом или «на всякий случай» guard не ставится.
10. **Шаг, закрытый фикстурой.** Шаг-подготовка (создать сущность, получить токен), который ровно делает фикстура контура и падает при неуспехе, закрывается фикстурой; запрос и его проверку в тесте не повторяй.
11. **Шаг вне API.** Состояние, недоступное через API и контур (настройка в админке, БД без клиента), не проверяй выдуманным способом. Есть клиент или фикстура — используй; нет — считай шаг предусловием окружения, не включай в код и укажи в отчёте, что не автоматизировано и почему.
12. **Проверяй поле, которое фиксирует факт, а не подстроку.** Одно значение может встречаться в ответе в разных ролях (список вариантов, эхо запроса, справочник), и только одно место означает проверяемый факт. Особенно для отрицаний («X нет», «Y не произошло»): отсутствие подстроки ничего не доказывает. Принятые в проекте способы проверки типовых фактов — в `code-patterns.json` → `domain_checks`. Непонятно, какое поле фиксирует факт, — `requires_operator_input`.
13. **Пример противоречит ожидаемому результату** (другое значение, нет поля, пример обрезан или от другого запроса) — побеждает текст ожидаемого результата; противоречие отметь в отчёте как замечание к кейсу.
14. **Негатив без отличия от позитива.** Кейс заявляет условие (другая роль, невалидные данные, несуществующая сущность), а входные данные такие же, как у позитивного варианта, — `requires_operator_input`: тест не проверит заявленное.

## 🧠 Принципы теста

1. **Один кейс — один тест-метод.** Шаги кейса — последовательные `allure.step` внутри метода. Не дроби кейс на несколько тестов по шагам или критериям.
2. **Трассируемость:** требование → кейс → тест → результат.
3. **Независимость и идемпотентность:** тест не зависит от других тестов и от прошлых запусков, повторный запуск не ломает состояние.
4. **Данные** — только из фикстур, конфигов или билдеров.
5. **Код читается как документация**, без поясняющих комментариев.
6. **Переиспользуемые фикстуры — только в `<test_root>/conftest.py`**, рядом с существующими. В тест-файле их не переопределяй, только используй. Вспомогательная функция, нужная одному сьюту и отсутствующая в контуре, — в `conftest.py`/helpers или, если это оправдано, в тест-файле. Клиенты, модели и билдеры — всегда в своих каталогах, не в тест-файле.

## 🚫 Общие запреты

- Не начинай генерацию без конкретного тест-кейса и без анализа требований.
- Jira MCP не настроен — не ходи по ссылке, попроси скопировать шаги.
- Не создавай модели, фикстуры, билдеры, если есть готовые; не игнорируй паттерны проекта.
- Не отдавай код без проверки на работоспособность; не оставляй TODO и заглушки без объяснения.
- Не правь код, если проблема непонятна, — запроси уточнение.
- Существующий тест правь точечно: не переписывай целиком и не меняй архитектуру без согласования.
- После генерации новые сценарии не добавляются.
- Внешний блокер (стенд недоступен, 4xx/5xx из-за данных, не хватает входных) записывай в `.gigacode/design/fix-history.md`, а не только в ответ: причина должна пережить паузу.

## 🛠️ `<test_root>` и `<test_suites>`

`<test_root>` — корень тестового дерева. Определяет оркестратор один раз в начале и передаёт всем агентам; агенты его не переопределяют. Первый сработавший шаг:

1. Путь, указанный оператором.
2. Каталог с `conftest.py` (поиск до 3 уровней от корня репозитория).
3. Каталог с `pytest.ini`/`pyproject.toml`, если в нём есть тесты; иначе `tests/` рядом.
4. `tests/`, если в корне есть `requirements.txt` и `tests/`.
5. `code-patterns.json` → `project_context.test_root` — только подсказка; если расходится с фактом, верен факт.
6. Иначе `tests`.

`<test_suites>` — каталог тест-файлов: из `code-patterns.json` → `project_context.test_path_pattern` (где лежат существующие `test_*.py`); если тестов нет и каркас собран bootstrap'ом — `<test_root>/rest/test_suites`; иначе `<test_root>`. Тест всегда пишется и запускается как `<test_suites>/test_<feature>.py`.

**Структура есть — она рабочая.** Не навязывай свою схему папок и не перестраивай существующее; добавляй только то, чего не хватает для кейса. Если структуры нет вовсе, каркас из шаблонов собирает оркестратор (`skills/api-test-generation/SKILL.md` → «🏗️ Bootstrap»).

## 🏷️ Маркеры интеграции

Механизм отметки статуса теста для отчёта (pytest-маркер, allure-метка и др.) в каждом проекте свой.

- Бери его из контура (`conftest.py`, существующие тесты, `pytest.ini`, `code-patterns.json` → `markers`). Не хардкодь имя (`zephyr`, `jira` и т.п.) и не переноси из другого проекта.
- Механизм есть — ставь такой же в новых тестах. Нет — тест без маркера.
- У существующих тестов маркеры не удаляй и не переименовывай без решения оператора.

## 🖥️ Shell-команды

Выбирай формы, которые не требуют подтверждения; рабочий каталог задавай параметром `directory` (корень проекта), а не через `cd`.

- Можно: `python -m pytest …`, `python -m py_compile …`, `python -c "…"`, `git …`, `ruff …` — из корня проекта.
- Нельзя: `cd /абсолютный/путь && …`, heredoc, `rm -rf`/`rm -f`, чтение файлов вне проекта, `find` с фильтрами. Вместо них — `read_file`/`glob`/`write_file`/`edit` или `python -c` из корня.
- Удаление временного файла — `python -c "import os; os.remove('…')"`.
- Команда отклонена (deny) — это не блокер и не повод спрашивать оператора: сразу попробуй эквивалентную разрешённую форму.
